# Direct RDS versus PgBouncer WAL commit probe — 20 September 2026

This was a bounded diagnostic on the isolated Huawei RDS instance, **not** a ticketing capacity qualification. Source: commit `697a637` (`scripts/wal_path_probe.py`). The running ticketing services remained on `d5ff3e3`; no application image or RDS parameter was changed. The four-block test ran from **05:52:10 to 05:58:11 UTC**. Both paths passed preflight against the same database and role with `synchronous_commit=on`, `fsync=on`, and read-write transactions. The direct diagnostic connection used encrypted `sslmode=require`; it did not validate the RDS certificate because the existing private CA setup is unresolved.

A uniquely named logged table received 8 KiB payload inserts at **40 transactions/s** for 90 seconds per block, with 16 preconnected clients and order direct → pooled → pooled → direct. Each block completed all 3,600 transactions with **zero errors** and scheduling lag below 20 ms. The table was dropped by the probe and an independent catalogue check found **zero** `capacity_wal_probe_%` tables afterward. The API returned ready after the run.

The independent RDS observer collected **4,000 samples at 100 ms with zero query errors**. In each block, the observed WAL increase was about 35–36 MB. Neither `wal_buffers_full` nor requested/timed checkpoint counters increased within any block. WAL sync and WAL write waits were sampled in both paths; the final direct block had 311 samples containing `WalSync` and 68 containing `WALWrite`, versus 25 and 1 in the clean third block. All 64 commits above 100 ms had a WAL wait event sampled within the commit interval expanded by 100 ms on either side. This is temporal association, not exact backend-level attribution: the observer samples all database sessions and can miss or overassociate short waits. `track_wal_io_timing` was off, so RDS reported zero WAL write/sync timing and cannot separate storage service time from internal WAL contention.

**Conclusion:** PgBouncer is not required to reproduce the intermittent long commit, since 50 of 7,200 direct transactions exceeded 100 ms. The paired 7,200 pooled transactions had 14 such commits, so this test does not support PgBouncer as the sole cause. The large block-to-block variation makes a precise path ranking unreliable. The evidence implicates the RDS WAL write/sync path; it does **not** yet prove an underlying disk fault or identify a safe parameter fix. The current `max_wal_size`, `wal_buffers`, and `wal_compression` settings should not be changed on this evidence: there were no probe-window checkpoints or buffer-full events. Huawei's parameter templates do not expose `track_wal_io_timing` for this instance, and the application role cannot set it.

## Huawei Cloud minute-level I/O metrics

User-supplied Cloud Eye screenshots cover **20 September 2026, 12:50–13:00 Bangkok time**, including all four probe blocks. For that ten-minute view, Write I/O Latency is **0.31–0.80 ms** (average **0.534 ms**), Disk I/O Wait Time Percentage is **0.42–2.68%** (average **1.19%**), and Write IOPS is **105.11–190.17/s** (average **155.134/s**); Read IOPS and Read I/O Latency display zero. The I/O wait high point appears at approximately **12:57**, during the final direct-RDS block (12:56:41–12:58:11), which had 43 commits over 100 ms. This is a minute-level temporal coincidence, not proof of a storage fault.

Huawei [defines Write I/O Latency as average disk response time](https://support.huaweicloud.com/intl/en-us/usermanual-rds-pg/rds_pg_06_0001.html), with a one-minute raw monitoring interval. Therefore the dashboard's “Max/1 minute” display is **not the maximum latency of an individual write**. Its 0.80 ms high point can coexist with a 416.83 ms client-observed commit. Similarly, I/O wait is CPU time spent waiting for disk I/O, not a direct WAL fsync latency measurement. These graphs do not show sustained minute-level disk saturation, but cannot resolve the subsecond WAL waits sampled by PostgreSQL. Provider-side traces are unavailable, so continue with the self-service diagnostics below.

## Self-service follow-up without provider traces

A second pass over the private per-transaction rows found that the final direct-RDS block's **43 commits over 100 ms formed five bursts** between **12:57:17 and 12:57:23 Bangkok time**, using a 100 ms inter-burst gap. The largest burst contained 13 such commits within about 418 ms. This favors a short shared stall over 43 independent slow statements, but does not identify which backend or I/O operation initiated it.

A bounded direct-RDS diagnostic is now implemented in [`wal_pid_probe.py`](../../../../scripts/wal_pid_probe.py): it records `backend_pid` on each probe connection and samples `pg_stat_activity` for those exact PIDs during each measured commit. Its Huawei run remains pending SSH access. This closes the current attribution gap: the existing observer only aggregated all sessions. Keep the same isolated table, SQL, write volume, rate and cleanup gate. Run matched 4-connection and 16-connection blocks at the same offered rate, in alternating order, to test whether client concurrency raises `WALWrite` contention. Report whether slow commits coincide with the **same backend** waiting on `WalSync`, `WalWrite`, `WALWrite`, replication or another event. A missed 20–50 ms sample is inconclusive; measure observer overhead and clock alignment. None of this changes the ticketing transaction path or its durability settings.

If the backend-level evidence still points to WAL, compare a **separate disposable PostgreSQL instance** with the same probe as a control. Different hardware and configuration prevent a definitive RDS-versus-PostgreSQL verdict, but can reveal whether the burst is specific to this managed instance. PostgreSQL 17's [`pg_stat_activity`](https://www.postgresql.org/docs/17/monitoring-stats.html) exposes backend PID and wait events, while `pg_stat_wal` exposes WAL write/sync counts even with `track_wal_io_timing=off`; `pg_stat_io` tracks relation I/O rather than WAL. A controlled probe cannot qualify 750 RPS ticketing capacity. Keep admission controls and synchronous durability in place; any ticketing persistence or scaling change requires an ADR first.
