# Read-only durability audit comparison

Date: 2026-09-29. Both variants audited the same completed Huawei RDS/DCS 1,000 RPS / 30-second fixture from stage `20260928T165459Z-0c0dcd09`. No new load was generated. The dataset contained approximately 2.41 million idempotency records, 677,000 reservation commands and 32,311 historical Redis reservation-stream keys.

| Phase | Grouped SQL, sequential Redis | Grouped SQL, pipelined Redis |
| --- | ---: | ---: |
| Idempotency/hold/order links | 2.168 s | 2.259 s |
| Durable reservation commands | 0.676 s | 0.650 s |
| Seat-ownership overlap | 2.104 s | 2.028 s |
| Redis stream entries/pending | 155.037 s | 3.652 s |
| **Total** | **160.015 s** | **8.619 s** |

The resulting per-run counts, 1,800 audited holds, zero overlap and every queue count matched the original passed stage exactly. The optimized verifier still scans the full Redis keyspace and checks both `XLEN` and `XPENDING` for each stream; it batches up to 256 keys per pipeline. A nonempty stream without its consumer group fails the audit. The change affects only read-only validation; it does not change booking or payment behavior. [ADR 0080](../../../adr/0080-batch-read-only-durability-audit.md) records the decision and failure behavior.

The historical read-only comparison alone does not establish production throughput.

The first controlled stage using the verifier ran at 1,000 requests/s for five minutes with eight generator workers, delta seat-map reads and 6% Redis-first reservation writes. It sent 300,000 requests (282,000 reads and 18,000 holds) with no generator drops, transport errors, retries or admission rejections. The worst worker's read p95 was 12.25 ms and hold p95 was 27.91 ms. The fixed post-TTL audit matched all 18,000 acknowledged holds to durable commands, found zero overlapping seat-ownership intervals, and found no undrained queues. The full audit took 9.77 seconds, including 4.28 seconds to inspect all 33,111 historical Redis reservation streams. The seat-map delta observer recorded zero version-chain anomalies over 475 samples. Every stage gate, including deployment rollback, passed. The source revision was `73cbd21`; the stage ID was `20260928T173314Z-ab2b5f06`. This is a five-minute capacity result for this workload and topology, not a production capacity guarantee.

The 800 synthetic sale fixtures were retired after the stage. A follow-up inventory check found zero active synthetic capacity and zero pending reconciliation work. A second stage used the same settings for 15 minutes. Its compact evidence is linked below.
The 15-minute stage (`20260928T174338Z-2d78fa08`) also passed every gate at source revision `73cbd21`. Its eight generators completed 900,000/900,000 requests: 846,000 delta seat-map reads and 54,000 Redis-first holds. There were zero drops, late deliveries, transport errors, retries and admission rejections. Worst-worker p95 was 12.47 ms for reads and 27.67 ms for holds. After the 130-second expiry wait, all 54,000 provisional acknowledgements had matching durable commands and hold/order/idempotency links. The full interval audit found zero overlapping holds; outbox, refresh, dead-letter and Redis reservation-stream queues were empty. The audit scanned 33,911 historical Redis stream keys and finished in 13.07 seconds. The delta observer found no chain anomaly over 1,082 samples. The reservation writer reported 54,000 durable outcomes and no failures. Kafka lag peaked at 52 messages and returned to zero. The stage rollback passed. Its 800 synthetic fixtures were retired afterward; inventory and pending reconciliation returned to zero.

The validated planning point for this exact synthetic mix and Huawei topology is 1,000 total requests/s for 15 minutes, including 60 reservation requests/s. This does not establish peak RPS, 30-minute endurance, hot-seat contention performance or payment throughput. All holds here received HTTP 202 until durable processing completed; the audit checked those durable outcomes explicitly.
