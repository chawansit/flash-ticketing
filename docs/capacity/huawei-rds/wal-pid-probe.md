# PID-correlated WAL probe

The diagnostic in scripts/wal_pid_probe.py runs only against a direct PostgreSQL connection and a disposable logged table. It records the server backend PID and exact client-observed commit interval for each insert. A separate direct connection samples pg_stat_activity for those PIDs every 20 ms. It then counts wait events sampled on the same PID during each commit exceeding 100 ms. This is stronger attribution than aggregate wait samples, but it still cannot measure the internal duration of an RDS fsync or prove that storage caused the wait.

Use the existing isolated Huawei test RDS and API ECS. Confirm the API is ready, no capacity stage or backup overlaps, the RDS is writable, and the private direct TEST_DATABASE_URL in the Compose tests service reaches the intended RDS. The preflight checks synchronous_commit=on, fsync=on, and a read-write transaction; it creates no table. The RDS diagnostic uses encrypted sslmode=require because the existing CA setup does not validate this endpoint. Application TLS settings remain unchanged.

Run with a fresh private output directory mounted into the tests container. Defaults are bounded to 40 inserts/s for 120 seconds, 16 preconnected direct clients, one incompressible 8 KiB payload per insert, and 20 ms wait sampling. Do not run a capacity stage at the same time. The script writes a recovery marker with the exact disposable table name before creating it, drops that table on normal exit, and reports cleanup_pass. If interrupted, use the marker to inspect and drop only that exact table after confirming no probe process remains. Keep raw transaction and PID samples in ignored tmp storage; publish only a redacted summary.

A valid run requires all scheduled transactions to complete with zero errors, scheduler lag below 100 ms, at least 80% of expected observer samples, zero observer query errors, and successful cleanup. A slow commit with no same-PID sample is inconclusive. PostgreSQL reports WalSync for waiting for WAL durability, WalWrite for a WAL-file write, and WALWrite for the lightweight lock protecting WAL writes; distinguish event names and types. Sampling can miss brief waits or observe multiple states during one commit.

Local integration validation on 20 September 2026 used the repository's PostgreSQL 17 container and the explicitly local-only --local-no-tls switch. It completed 1,200/1,200 inserts at 40/s in 30 seconds with zero errors, 1,498 wait samples/zero observer errors, six commits over 100 ms, and zero residual probe tables. Same-PID wait classifications were WalSync (one), WALWrite (four), and ClientRead,WALWrite (one). These local numbers validate the probe mechanics, not Huawei capacity or the source of its commit spikes. The local PostgreSQL container was returned to its prior stopped state. The Huawei run is pending SSH access; no RDS PID-probe data is claimed.
