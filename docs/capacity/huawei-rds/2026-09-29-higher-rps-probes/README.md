# Higher-RPS Huawei capacity comparison

Date: 2026-09-29 Asia/Bangkok. These stages used four API replicas, three reservation writers, eight load-generator workers, the same Huawei RDS/DCS topology and fresh 800-show synthetic fixtures. Traffic was 94% delta seat-map reads and 6% Redis-first holds, without retries. The oldest reservation command guard stayed at 60 seconds. Application code and the strict acceptance gates did not change between stages; source revisions `d378161` and `85d7792` differ only in capacity documentation.

The first 1,100 RPS 30-minute run missed one scheduled hold because generator worker 5 was 50.0005 ms late against the fixed 50 ms drop threshold. It was not an API failure: every transmitted request succeeded, and the writer made every accepted hold durable. The result remains a failed strict stage. An unchanged 30-minute repeat sent every request and passed all gates. In that repeat, writer command age averaged 1.48 seconds with p99 in the <=5-second bucket; the post-TTL audit checked all 118,800 holds and all 38,711 historical Redis reservation-stream keys in 23.81 seconds. The delta observer found zero version-chain anomalies over 1,998 samples. Kafka lag peaked at 53 and returned to zero, although observed drain from its peak took 295 seconds; downstream event latency needs a separate SLO assessment.

The 1,200 RPS five-minute pass did not predict sustained success. After several minutes at 1,200 RPS, the per-show Redis intake guard returned 32 `RESERVATION_PERSISTENCE_LAGGING` responses across all four API workers. It rejects a new hold when that show's oldest reservation command reaches the configured 60-second age limit, protecting against an acknowledgement that cannot be made durable before expiry. These 32 responses are real failed requests: 0.00296% of all 1,080,000 requests, or 0.0494% of 64,800 hold attempts. They were not retried or excluded from the gate. All 1,015,200 reads returned HTTP 200. The accepted 64,768 holds all became durable, with no broken links or overlapping seat intervals, and queues drained. The writer reported no database exception or failed persistence outcome; the available evidence does not isolate PostgreSQL WAL, writer scheduling or stream distribution as the sole cause of per-show lag.

The confirmed planning point from these measured stages is **1,100 total RPS for one passing 30-minute run, including 66 hold requests/s**, on this topology and disjoint-show workload. The first 30-minute run's generator drop and the 1,200 RPS sustained rejection remain part of the record. This does not establish a production SLA, maximum RPS, hot-seat contention capacity, payment throughput or failover recovery. Each stage restored the original topology, retired its synthetic sale fixtures without deleting data, and reached zero active test capacity and zero due reconciliation work.
