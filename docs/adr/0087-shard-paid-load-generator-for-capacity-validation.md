# 0087 — Shard the synthetic paid-journey generator before attributing backend capacity

- **Status:** Accepted as a bounded diagnostic design, not a production traffic-shaping choice.
- **Context:** One Python process with a shared HTTPX client dispatched every scheduled buyer at 45/s but failed repeated 60/s stages. An HTTPX trace at 60/s found hold/payment pre-send p95 6.10/6.75 s while response-header wait was 42/91 ms and FastAPI `Server-Timing` 11.91/60.44 ms. Raising the HTTP connection cap from 500 to 1,000 without changing the 500-journey cap worsened pre-send p95 to 7.28/7.50 s and yielded 1,049 generator drops. The shared client and one event loop may be the limiter; a backend capacity claim is invalid while the generator drops work. The failure still yielded exact post-TTL paid-ticket audits and zero double booking. ADR 0086's pool-headroom candidate is not promoted.
- **Decision:** For a 60/s diagnostic, split one private development fixture into two disjoint show sets and viewer-token subsets. Launch two generator processes on the existing 8-vCPU/16-GiB generator ECS, each scheduling 30/s for 60 seconds and allowing 250 in-flight journeys with a 250-connection client pool. Coordinate a common future start time so combined offered load is 60/s from the beginning. Preserve one callback/payment, 0.2 s polling and zero retries. Aggregate counts by sum and use the worse shard p95 as a conservative label, not a true combined percentile. A strict pass requires both shards to pass individually, 3,600 unique paid tickets by deadline, exact post-TTL audit, queue drain, zero double booking and rollback. Keep the four-consumer backend candidate and all other settings fixed. An opt-in two-shard CLI retains the existing one-process default.
- **Alternatives:** Raising a single process's connection limit already failed. Raising its journey cap from 500 to 1,000 could accumulate more delayed work and conceal queueing. Adding a second generator ECS would increase cost before checking whether two processes on the existing ECS suffice. Using the same show IDs for both shards risks artificial seat contention and invalid aggregate uniqueness. Comparing average shard p95 as an overall percentile would understate tails.
- **Consequences:** Two event loops and pools remove one shared client bottleneck but double process overhead; aggregate generator CPU and file descriptors must be observed. Distinct show sets preserve one seat per scheduled buyer and prevent cross-shard booking conflicts. More honest offered traffic may expose API, payment simulator, Kafka or PostgreSQL limits. A one-minute pass is not a one-hour production capacity estimate. Overall rate and total in-flight budget remain fixed for a fair diagnostic.
- **Failure/recovery behavior:** If either shard cannot start before the common schedule, produces no result, drops work, returns unexpected outcomes or fails its own strict gate, mark the combined stage failed. Preserve each redacted shard result, terminate remaining shard processes, run the same post-TTL audit for accepted buyers and restore the backend topology. A crash after payment initiation can be ambiguous; reconcile by durable order/payment/ticket state rather than assuming a retry succeeded. Private split manifests are created with restricted permissions and deleted after the run.
- **Validation evidence:** The [single-process pool trace](../capacity/flash-sale-opening/paid-ticket-client-pool-trace-2026-09-29.json) and [failed pool-headroom comparison](../capacity/flash-sale-opening/paid-ticket-client-pool-headroom-2026-09-29.json) motivate the design. Before running the candidate: unit tests for disjoint seats and tokens, synchronized schedule and conservative aggregation; then a cloud preflight, 60/s shard stage, post-TTL exact audit and rollback. No two-process result exists at decision time.
