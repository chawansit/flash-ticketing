# 0110 - Measure development payment dispatch phases

- **Status:** Accepted before implementation on2026-10-03. User approved the ten-step improvement plan; this implements its first diagnostic step.
- **Context:** Fixed-total two-process60buyers/s300s control at44a1c95 failed with2572drops and54customer503s. Due-to-callback statement proxy p95 was8590ms versus callback-to-ticket284ms. Existing aggregate worker busy time cannot separate claim/HTTP/acknowledgement or slots parked behind the batch barrier. Four API pool rejection counter increments were not attributed to customer503s.
- **Decision:** Add bounded-label phase histograms for claim, HTTP delivery and delivery acknowledgement; measure due-to-claim age using a timestamp in the existing claim query and batch-barrier slot seconds. Collect those metrics in the existing observer and summary, including webhook503 routes. Preserve SQL locking/15s lease/token fencing, external HTTP outside transactions,5s HTTP timeout, callback IDs and all worker budgets. No customer/order IDs, payloads, credentials or SQL text in labels. This extends observability without changing persistence or payment semantics.
- **Alternatives:** More concurrency without phase measurements hides the mechanism. Per-payment trace labels create unbounded cardinality. Additional per-callback DB timestamp queries add round trips.
- **Consequences:** Histograms add small measurement overhead; use identical instrumentation in both comparison arms. Bucket p95 is an upper bound, not an exact quantile. Due-to-claim is a DB-clock statement proxy, not exact commit time. Batch idle measured when completed futures are observed is a conservative diagnostic, not total machine idleness.
- **Failure/recovery behavior:** Metric collection cannot alter claim/ack transactions or retry outcomes. Keep existing lease recovery and duplicate callback safety. Missing/reset counters invalidate phase attribution. Restore baseline and audit exact paid/unpaid cohorts after original hold deadlines, zero duplicates/extra events and full queues/Kafka on every cloud arm.
- **Validation evidence:** Pending focused diagnostics tests and appropriate unit/integration checks. Compare one instrumented batch baseline at60buyers/s300s before ADR0111 candidate. A baseline performance failure is recorded honestly; progression to the same-rate scheduler candidate requires correct paid/unpaid/TTL/queues/source/observer gates. No rate escalation.
