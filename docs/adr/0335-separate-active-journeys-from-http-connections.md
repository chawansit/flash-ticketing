# ADR0335: Separate active journeys from HTTP connection capacity

## Status
Accepted for one bounded paid comparison after local verification. The user explicitly approved the concrete800/500-slot160/s300-second request; one fresh paid-stage allowance is now registered, with a3600-second whole-experiment bound and unchanged resources/quality gates. Cloud capacity is not yet measured.

## Context
ADR0333 offered160 journeys/s for300 seconds with four processes and500 active journeys/500 HTTP connections/16 clients. Four complete raw reports recorded40095 dispatched/paid/issued and7905 active-capacity drops. Mean successful journey residence was3.68s and generator CPU approximately0.55 cores/process. Little's law suggests589 active journeys at160/s before headroom. Both initial payment errors recovered, and fresh financial reconciliation passed; the original quality test remains failed. Best qualified clean short throughput remains138.49 tickets/s. This is evidence of a generator occupancy constraint, not proof that the application will sustain160/s with more concurrency.

## Decision
Prepare an explicit source-bound ADR0335 profile with800 active journeys: four processes at200 each. Preserve500 total HTTP connections (125/process),16 HTTP clients (4/process),160 offered journeys/s for300 seconds,48000 scheduled journeys,160 isolated shows, gateway timing, polling and bounded recovery. Four API/fifteen worker pods, image, resources,24 physical database backends, admission20 and API2+2 slots remain unchanged. Require the immutable failed ADR0333 evidence and its successful operational recovery as the comparison reference, alongside existing lower-rate qualification. Do not register another paid allowance during preparation.

The historical leaf validates HTTP connections >= active journeys. Adapt only that resource-validation expression in the new profile: explicitly require200 active journeys,125 HTTP connections and4 clients per child. Retain its request/recovery/seat/payment code byte-for-byte otherwise; fail closed if the expected source expression changes. Historical ADR0333 keeps the sealed leaf and500/500 limits. Source/configuration contracts, launch arguments, metadata and accounting must agree on800/500/16 before deployment. Close the failed-dispatch diagnostic gap so an after snapshot is attempted even when dispatch raises, without replacing the original exception.

## Alternatives
Keep500 slots and first shorten journey residence: useful application work, but it cannot isolate whether the current admission cap hides capacity. Increase HTTP/database connections along with journeys: confounds the comparison and risks downstream overload. Increase offered rate or move the generator to CCE: changes more factors. Raising active slots to600 leaves little headroom against the measured mean;800 is bounded and permits roughly5 seconds average residence at160/s.

## Consequences
More journeys may wait concurrently and create more actual traffic.800 slots do not guarantee zero drops, unchanged latency or160 successful tickets/s. Retain all existing latency gates, zero generator drops, final customer failure <=0.01%, zero double-booking/payment loss, post-TTL financial verification, queue drain and exact restoration. Supersedes ADR0333's500 active-journey limit and sealed-leaf resource validator only when ADR0335 is explicitly selected. No persistence, locking, messaging, idempotency, TTL, gateway or application scaling decision is superseded.

## Failure and recovery behavior
Reject partial selection, stale source seals, changed connection budgets, image/configuration drift and missing original/recovery evidence. Require fresh authorization for one paid stage, bounded to3600 seconds including setup and restoration. Stop escalation on arrival/latency/customer/financial failures; preserve raw reports and the original failure. Capture diagnostics on both success and failure, complete mandatory audit/drain, remove owned resources and restore runtime. Never replay ambiguous payments with a new idempotency key. A diagnostic failure must be visible and must not mask the customer-stage failure.
