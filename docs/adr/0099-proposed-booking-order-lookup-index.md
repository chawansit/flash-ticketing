# 0099 - Booking order lookup index

- **Status:** Accepted for a controlled candidate on 2026-10-03, before implementation; no capacity promotion before validation.
- **Context:** ADR0098 fixed the historical payment scan and the short45/s paid control passed2700/2700. Callback-to-ticket p95 remains8.39s. Both the consumer booking lookup and authenticated ticket-list query filter bookings by order_id; the populated table only has the id primary key and unique(event_id,seat_id). Idle read-only plans on a completed fixture scanned66,532 bookings, filtering66,531 to retrieve one row, taking4.914ms and4.831ms. This establishes avoidable history-dependent work, not loaded cost or sole Kafka delay cause.
- **Decision:** Add an additive nonunique B-tree bookings(order_id), retaining the seat uniqueness constraint and allowing up to eight bookings/order. Use bounded concurrent creation on populated cloud data, verify relation/key/predicate/validity, and ordinary migration on fresh/local databases. Do not batch ticket issuance, change inbox/commit boundaries, add retries, scale workers or alter TTLs in this candidate. Use index name bookings_order_id, ordinary migration008_bookings_order_index.sql, and the existing bounded online-build/definition verification pattern.
- **Alternatives:** Covering index(order_id) INCLUDE(id,seat_id) adds size/write amplification; increasing consumer replicas changes partition assignments and DB budgets; worker/commit phase instrumentation may be needed if the lookup change does not reduce residual delay. Dropping existing seat uniqueness is unacceptable.
- **Consequences:** Per-order lookups should avoid scanning completed booking history; each booking adds an index entry and associated WAL. Nonunique order_id supports multi-seat orders. This extends physical access only and must not supersede PostgreSQL seat authority, idempotency, inbox/outbox, payment or TTL decisions. No throughput benefit is claimed before measurement. No accepted seat/booking uniqueness, inbox, payment or TTL decision is superseded.
- **Failure/recovery behavior:** Bound online build by statement/lock timeouts and stop on invalid or unexpected definitions. Keep current lookup behavior if no index exists. Remove only a verified owned candidate if correctness fails; retain the valid lookup index only if query-plan benefit and correctness audits pass, and record it separately from service-config rollback if customer gates fail. Concurrent build uses60s statement and1s lock timeouts; an invalid or conflicting existing index blocks the candidate.
- **Validation evidence:** Proposal evidence is the redacted final read-only plan in [ADR0098 control](../capacity/flash-sale-opening/real-paid-payment-index-control-2026-10-03.json). Planned validation (now executed below): multi-seat booking/ticket correctness and duplicate-event tests, valid index verification, before/after same idle queries, then same45/s cache-enabled profile against source3ae6bf7. Require zero drops/customer errors, exact post-TTL tickets/zero double booking, queues/Kafka drain and configuration rollback. The controlled candidate covers only the same45/s profile; no higher-rate test or consumer scaling is included.
