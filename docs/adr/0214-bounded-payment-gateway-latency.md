# 0214 - Bounded payment gateway latency

- **Status:** Accepted before implementation on 2026-10-07. Implemented and locally qualified; cloud deployment and capacity qualification pending.
- **Context:** The user approved synthetic gateway initiation latency of 50â€“150 ms, confirmation delay of 1â€“3 seconds, and callback network latency of 20â€“100 ms. A high-capacity provider still has latency. These ranges are test assumptions, not banking measurements. Latest paid control deliberately used zero confirmation delay; it failed and remains recovery-required. Historical evidence must not be rewritten or compared as though gateway delays were unchanged.
- **Decision:** Add the development simulator's `bank-like` latency profile, selected by `SIMULATOR_LATENCY_PROFILE` and used by default for new local deployments. Use bounded uniform jitter for initiation and callback transport. Derive confirmation jitter deterministically from the actor, order and idempotency key so retries have identical financial request parameters. When `delay_seconds` is omitted, schedule confirmation 1â€“3 seconds after payment persistence. Explicit numeric delay overrides remain available; `none` retains the legacy omitted-delay default of one second and disables artificial initiation/transport waits. Initiation awaits without occupying an API worker thread or database connection; database work remains in the existing thread pool. Confirmation uses the durable `due_at` timestamp, not a sleeping worker. Callback transport delay occurs after claim commit and before HTTP delivery, with no database connection held. Record configured delays separately from due-to-claim lateness and actual callback HTTP processing.
- **Alternatives:** Zero-delay providers are useful controls but omit latency. Sleeping through confirmation inside a transaction wastes connections and risks starvation. Random confirmation resampling on each idempotent request changes its fingerprint. A new external gateway service is unnecessary for this bounded implementation and would be a separate placement/capacity experiment.
- **Consequences:** Deliberate delays increase end-to-end journey latency and in-flight payments. The short callback transport wait occupies an existing bounded simulator slot; it does not establish high simulator throughput. No concurrency, machine size, connection budget, financial transaction, hold TTL, callback ID, Kafka semantics or SLO gate changes. Existing generators explicitly sending `delay_seconds=0` override confirmation jitter; future realistic-profile runs must omit that override and bind the profile in their configuration. No existing frozen cloud image, registered scope or runner is changed by local implementation.
- **Failure/recovery behavior:** Preserve 15-second claims, token-fenced acknowledgements, stable callback IDs and lease-based redelivery without inline HTTP retries. Reject unknown profiles. Keep all delays outside database transactions. Replayed payment requests remain stable and customer authorization remains enforced. Keep zero double-booking, durable payments, post-TTL checks and full queue drain. Original failed recovery still blocks further cloud experiments.
- **Validation evidence:** Executed 63 focused unit and 36 real PostgreSQL/Redis integration tests; all passed. Jitter bounds, explicit overrides, stable confirmation selection, asynchronous initiation, transaction-free waits, callback replay, acknowledgement fencing and payment durability are covered. Detailed executed evidence is recorded below. No cloud load or capacity improvement measured.

This selectively supersedes the legacy fixed one-second omitted payment delay for the `bank-like` profile. ADR0004 payment idempotency, ADR0110 phase diagnostics, ADR0111 bounded refill scheduling, ADR0121 callback transport and ADR0189 claim fencing remain in force.
