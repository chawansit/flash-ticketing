# 0113 - Nonblocking reads during a bounded reservation-stream sweep

- **Status:** Accepted for implementation and a same-rate controlled experiment on 2026-10-03, before code changes. User-approved conditional improvement roadmap. No higher-rate stage is authorized by this decision alone.
- **Context:** ADR0112's twelve-slot refill control at60 buyers/s300s failed296drops/32customer503s. Callback due-to-delivery proxy p95 remained416ms, while customer durable-confirmation p95 rose to20727ms and API mean pool wait to10.02ms. All17682paid tickets and3expired unpaid orders passed fresh post-TTL uniqueness/full-queue/Kafka/source/restoration checks. Code polls up to32 individual event streams using XREADGROUP BLOCK1; streams may have retained entries but no new entries because another writer already owns them. On isolated Redis7.4.5,31 no-new-entry streams before one ready stream took3094ms with BLOCK1 versus20.5ms without BLOCK. This reproduces the polling mechanism, not its exact share of Huawei latency or proof that twelve slots caused the regression. Redis documents blocking timeout resolution near0.1s: https://redis.io/docs/latest/commands/xread/.
- **Decision:** Omit BLOCK for each per-stream XREADGROUP in the existing bounded sweep. Keep separate event-slot reads, total remaining COUNT, reclaim-before-new priority,30s pending reclaim, rotating discovery, registry race recovery and PostgreSQL commit-before-Redis acknowledgement unchanged. Keep the existing worker100ms backoff when a whole iteration returns no work, and1s exception backoff; do not create a hot idle loop or use BLOCK0 (which blocks indefinitely). This supersedes only the blocking-read detail within ADR0058/0064 stream consumption, not their accepted delivery/fairness/slot-locality decisions. Keep twelve refill slots for the60/s300s comparison with d73ba3d, so polling is the sole application/configuration factor; all API/DB/consumer/generator budgets,60shows18000actors and audit gates stay fixed. Record historical fixture/discovery variation as a limitation. Restore default batch4 afterwards.
- **Alternatives:** More writers or callback slots adds pressure without removing per-stream waiting. Multi-stream XREADGROUP conflicts with cluster slot locality and COUNT is per stream, risking over-assignment. Delete pending/owned streams would lose recoverable work. Increase age/deadline limits or caller retries would conceal the failed control. Pipeline all reads can claim more than the transaction bound before it is enforced.
- **Consequences:** Sparse sweeps should reach ready streams faster; Redis call rate can rise because timeout waits disappear. Work remains bounded to32 streams per iteration and100ms whole-idle backoff. No promise of a production RPS increase; many shows, reclaim-only streams and DB contention still require measurement.
- **Failure/recovery behavior:** Redis failures retain existing reset/backoff behavior. A returned command remains group-pending until PostgreSQL commits and Redis acknowledgement succeeds; another writer reclaims only under the existing idle lease. Domain compensation, duplicate command/idempotency guards, original hold TTL and SQL seat locking remain unchanged. On any customer/drop/financial/observer/source/queue gate failure stop rate progression, retire fixtures, audit exact paid/unpaid afterTTL and restore services without deleting stream work.
- **Validation evidence:** Local mechanism diagnostic executed and its owned Docker container removed; raw evidence tmp/stream-blocking-diagnostic.json. Regression tests must reject blocking sweeps, prove ready work after inactive streams, preserve total COUNT and reclaim-before-new bounds. Existing integration tests must exercise reclaim, commit-before-ack, duplicate callbacks and concurrent seat safety. Cloud same-rate result pending. Ninety buyers/s and hourly proof remain future scope until a separately recorded passing control and authorized progression.
