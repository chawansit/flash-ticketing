# 0084 — Bound OrderPaid fulfillment batches

- **Status:** Proposed, deferred after the four-consumer diagnostic; implement only if subsequent evidence identifies per-OrderPaid database work as the limiting path.
- **Context:** The 45 paid-journeys/s, one-callback stage dispatched 2,268/2,700 buyers and dropped 432 at the generator's 500 in-flight cap. Hold-to-ticket p95 was 23.55 s; Kafka consumer-group lag peaked at 912 across all six partitions, then drained. PAID orders awaiting tickets peaked at 223. The existing consumer batches `SeatsChanged` only and commits each `OrderPaid` independently with inbox, order lock, booking lookup, ticket insert, status update and outbox event. This incurs a commit and several round trips per paid order. The durable-hold p95 of 10.71 s shows a separate upstream delay, so fulfillment batching alone may not pass the journey gate. ADR 0070 preserved individual transactions for business handlers; this ADR supersedes that choice **only for contiguous `OrderPaid` records**, retaining individual event identity and durable effects.
- **Decision:** Process at most the existing `CONSUMER_BATCH_SIZE` contiguous `OrderPaid` records per transaction. Insert all new inbox IDs set-wise; lock their orders in deterministic ID order; reject a missing or non-PAID order and roll back the entire batch. Insert one unique ticket per booking, set orders FULFILLED and insert a distinct `TicketsIssued` outbox event per accepted `OrderPaid` record. Keep all work and inbox IDs in one PostgreSQL transaction; commit Kafka offsets only after it commits. Flush at event-type boundaries and retain existing individual handling for other business events. Make the behavior opt-in for the diagnostic and default to the previous per-event path.
- **Alternatives:** Add consumers beyond two first could increase database connection and WAL contention without reducing work per event. Skip `TicketsIssued` events would change the contract. Acknowledge Kafka before the database commit risks event loss. Merge multiple `OrderPaid` event identities into one could break idempotent replay and notification accounting. A direct ticket issue in the webhook lengthens and couples the synchronous payment transaction.
- **Consequences:** Fewer commits and DB round trips may increase throughput, but one poison event can roll back a bounded batch and require existing retry/dead-letter isolation. A transaction holds multiple order locks briefly; the batch cap bounds lock scope and memory. Successful inbox replay remains idempotent, though a distinct new event ID for an already fulfilled order still follows current behavior and emits a notification. The batch metric must distinguish this path from per-event work.
- **Failure/recovery behavior:** Crash before DB commit leaves no inbox/ticket/outbox effects and Kafka replays. Crash after DB commit but before offset commit replays into inbox conflicts; unique ticket constraints prevent duplicates. If one record is invalid, rollback all and let the existing bounded retry then single-message isolation dead-letter the poison record. Preserve order within each Kafka partition; no cross-partition ordering is assumed. On any failed cloud gate, restore the original consumer behavior and topology, then audit after TTL.
- **Validation evidence:** The motivating failed stage and exact post-TTL audit are [recorded here](../capacity/flash-sale-opening/paid-ticket-kafka-lag-2026-09-29.json). Before enabling: unit/integration tests for duplicate IDs, distinct IDs for one order, mixed-type boundaries, poison rollback and replay after commit; full test/lint suite; then a strict 30/s control and a 45/s diagnostic with matching fixtures, callback policy and connection budget. Measure Kafka lag, paid-to-ticket latency, generator drops, publisher/consumer busy time, database waits, post-TTL exact tickets and rollback. No throughput improvement is yet claimed.

The four-consumer follow-up passed a one-minute 45/s stage but failed at
60/s with hold-to-durable p95 12.49 s, while peak PAID-to-ticket backlog
was 36. This does not justify implementing OrderPaid transaction batching
next. First split synchronous hold latency from reservation persistence
latency and measure the upstream work. The proposal remains unimplemented.
