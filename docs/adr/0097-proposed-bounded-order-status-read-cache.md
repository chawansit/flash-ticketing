# 0097 - Proposed bounded order-status read cache

- **Status:** Proposed; no implementation, deployment or validation yet.
- **Context:** The corrected sixteen-client generator delivered every buyer at 45/s, but order GETs and payments still encountered full DB pools. Each order GET currently uses a durable-store transaction, with measured mean connection occupancy around 35.7 ms across operations. Increasing generator efficiency exposes more actual backend work. Booking/payment correctness audits pass despite poor customer outcomes. A failed GET must not be hidden by load-test retries.
- **Proposed decision:** Introduce an opt-in Redis read-through cache only for authenticated order-status GETs, default disabled. Begin with at most 3 seconds of snapshot age. Populate only after an actor-scoped PostgreSQL read has completed successfully and released its connection. Use the primary Redis endpoint and an order-plus-actor-scoped key; check payload ownership and schema before returning it. Preserve the API response shape and document bounded freshness. Cache data is advisory: payment authorization, expiry, seat ownership, booking and ticket issuance must always use existing PostgreSQL transactions. Keep booking/hold TTLs, uniqueness, outbox and Kafka consumers unchanged. A future implementation must account for time spent obtaining the DB snapshot so slow cache population cannot extend its freshness budget.
- **Alternatives:** More DB connections (changes write budgets and can increase contention); longer client polling (changes user-observation latency and did not solve the measured gate); retrying failed requests (can amplify overload); a Kafka-maintained order projection (more ordering/replay/reconciliation complexity); separate read replicas (replication lag and additional infrastructure). The cache is a controlled first experiment, not an accepted replacement for an event-driven read model.
- **Consequences:** Repeated status reads may avoid DB acquisition, at the cost of bounded stale status/ticket visibility. No throughput improvement is claimed. Cache TTL does not release seats or authorize payments. Cache expiration is not refreshed by hits. Prevent older concurrent fills from extending or overwriting fresher data; specify/test the fill rule before implementation. Use bounded low-cardinality cache hit/miss/error/stale counters, with no actor/order IDs or secrets in labels. Public browser caching must remain disabled for these authenticated responses.
- **Failure/recovery behavior:** Redis miss/outage/corruption must fall back through the existing bounded DB pool, never return another actor's data or stale-success guesses. Do not cache errors or authorization failures. If cache outage increases DB pressure, existing bounded 503 behavior remains explicit; the cache cannot guarantee outage capacity. Expired entries recover from PostgreSQL. No mutation transaction depends on cache writes. Disabling the option restores current behavior. No database/Redis data clearing, resource-budget increase or retry is part of this choice.
- **Validation evidence:** Future only: unit tests for authorization/TTL/schema/error behavior; real PostgreSQL/Redis integration checks for stale fills and failure recovery; ten-journey cloud smoke; then the identified 45/s, 1 s-poll profile with the validated sixteen-client generator and unchanged budgets. Require customer gates, exact accepted-payment post-TTL audit, zero duplicate bookings, queue/Kafka drain and rollback. Stop escalation on any failure. Review this proposal and change status before implementation. This would add a read-cache pattern without superseding accepted seat-locking, payment-idempotency or outbox decisions.
