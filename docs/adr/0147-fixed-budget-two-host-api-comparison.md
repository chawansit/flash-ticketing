# 0147 - Fixed-budget two-host API comparison

- **Status:** Accepted for local preparation on 2026-10-05 before implementation. User Continue accepts the proposed scaling comparison. Live execution requires a supplied, independently verified second API ECS; no such host exists in the saved inventory. No cloud provisioning or paid run is claimed.
- **Context:** The frozen deb330e diagnostic dispatched 18,000 buyers at 60/s for 300 seconds and durably issued all 18,000 tickets, with two failed customer status reads and 21/22 paid gates passing. Offered-window API-host CPU averaged 91.058%. Four API replicas, Kafka and background services share one ECS. More API containers on the same machine do not add CPU capacity. ADR0146 measured idle observation overhead but did not explain the regression. Additional compute is a separate measurable hypothesis. Existing paid orchestration, CPU collectors and pipeline observation assume four local API containers and cannot qualify a two-host deployment unchanged.
- **Decision:** Prepare one matched comparison: four API processes on the primary host versus two on the primary and two on a new API-only host of matching 4-vCPU/8-GiB size. Keep the independent generator, frozen application image/source, RDS, DCS, Kafka, background workers and total database budgets unchanged. Use the existing Nginx instance with four explicit per-container private endpoints in both arms, identical least_conn, keepalive and no-retry settings; prepare primary private-port exposure and an API-only secondary Compose file. No new PgBouncer, migration job, Kafka broker or worker on the secondary. Both hosts use the same existing primary PgBouncer and DCS through restricted private networking. Export/import the exact baseline API image rather than rebuild a floating tag. Secondary API startup environment must be a private export of baseline API settings, with only DATABASE_URL network address and host publication changed. Preserve database credentials/database name and existing PgBouncer TLS behavior. No direct-to-RDS API connection or read-replica routing.
- **Budgets and workload:** Four APIs in both arms: pool4 each (16 total including payment partitions), payment2 each (eight of those 16), shared acquisition12 each, admission4 each, cache0. Same six consumers/pool8, three writers/batch4, simulator8/refill, maintenance/publisher/reconciler1, max-command-age60, PgBouncer24/reserve0/client160. Compare 60 buyers/s for300s, 60shows/300seats, 500 journeys, two generator shards/eight HTTP clients each, one-second polling, one callback delivery, zero customer retries. Keep all22 original paid gates. Customer status and callback errors are separate outcomes. A failed control remains failed; no unsafe correctness/source/restoration failure may be used to proceed. No automated higher-rate or hour-long stage in this first comparison.
- **Preparation:** Implement a secret-free, fail-closed inventory validator and fresh private bundle renderer. Require distinct verified machine identities, matching host sizes and pinned image/source/settings, four exact API endpoints, shared PostgreSQL/Redis authority, fixed PgBouncer budgets, unchanged background placement and no background services on the secondary. A public plan with placeholder roles is not a verified inventory. The preparation tool emits configs, gate contracts and explicit prerequisites only: it does not deploy, open security groups, generate traffic or pretend existing single-host observers support the new topology. Record local validation separately from live qualification. Remote collectors must gather both hosts and all four replica metrics over the same offered window before any paid run; cross-host contention/replay tests and restore must also be proven.
- **Alternatives:** Immediately migrate to CCE Autopilot/ELB changes orchestration, compute and ingress together; add a read replica without proof of read saturation changes routing/freshness; move background services at the same time confounds the compute experiment; reuse the generator as an API host reintroduces generator contention; duplicate PgBouncer24 on the secondary doubles the primary server budget. Defer these alternatives. Scaling without fixed connections is rejected.
- **Consequences:** The extra network hop to primary PgBouncer and remote upstream is part of the distributed topology. Record these latencies separately; a poor result does not automatically disprove useful compute scaling. Explicit four-endpoint routing is applied to both comparison arms to avoid a DNS fan-out imbalance. Additional compute can shorten scheduling/connection occupancy but cannot eliminate shared database or hot-seat serialization. Nginx and PgBouncer remain primary-host dependencies; this is capacity measurement, not production HA. Replica startup, health checks and process-local admission can produce imbalance and must be measured. No linear capacity gain or300000tickets/hour qualification follows from this preparation.
- **Failure/recovery:** Refuse a missing host, generator colocated with either API machine, changed application image/source/settings, public/wildcard/loopback backend bind, stale or malformed evidence, unexpected services, direct database route, changed pool budget, incomplete four-replica observation or missing gates. Require owner-scoped temporary keys and remove exact entries after live work under the existing user authorization. Preserve saved normal settings/private environment and LB config before mutations. Use fresh run IDs/artifacts, bounded readiness and child cleanup. First prove 100 simultaneous attempts for one fresh seat across both hosts produce one accepted hold and one durable owner, plus idempotent replay and payment duplicate handling. Financial/zero-double-booking/queue/observer/source failure stops the comparison. After either arm, exact post-TTL audit and global queues/Kafka drain, source/readiness/normal settings verification are mandatory. Restore the LB and four primary replicas, stop/remove only owned secondary API resources, and verify cleanup even on failure. If restore is unconfirmed, no later load. Primary data and shared services are never deleted.
- **Validation evidence:** Planned local tests for host/route identity, resource/source/authority/budget invariants, prohibited secondary services, fresh artifact ownership, fail-closed missing gates, generated Compose and no-retry Nginx. Live image transfer, private connectivity, env parity, readiness, cross-host concurrency, collectors, paid comparison and rollback remain unexecuted until the additional host is supplied and the multi-host orchestration adapter is qualified. Append executed local evidence only.

Extends [ADR0034](0034-fixed-budget-horizontal-api.md) from same-host to measured multi-host capacity and reuses ADR0040/0090 bounded controls. No accepted persistence, locking, messaging, idempotency, TTL or production scaling decision is superseded. ADR0143/0145 remain separate cloud-unqualified candidates. No CCE/ELB/RDS-read-replica purchase, automatic rate escalation, GitHub push or main merge.

Executed local preparation evidence (2026-10-05): 43 focused tests passed for independent hosts, matched placement, private endpoints, pinned image/source, freshness, shared authority/settings, fixed budgets, prohibited secondary services, missing/false/nonboolean gates and fresh output ownership. Ruff passed. Docker Compose validated both generated configurations with synthetic private settings; Nginx syntax passed using the cached baseline Nginx image in a networking-disabled temporary container, which was removed. The bundle enforces primary frozen image/no rebuild, baseline API settings and one private PgBouncer24; secondary starts only APIs. No cloud access, configuration mutation or paid load occurred. The additional API host is not supplied; multi-host deployment/observer/rollback adapter and live qualification remain pending.
