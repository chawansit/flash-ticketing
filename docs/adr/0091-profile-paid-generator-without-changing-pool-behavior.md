# 0091 - Profile the paid generator without changing HTTP-pool behavior

- **Status:** Accepted for bounded diagnostics only; production architecture unchanged.
- **Context:** ADR 0090 reproduced multi-second pre-send waits and 394 drops at 60 journeys/s against a valid loopback responder. HTTPcore 1.0.9 scans connections and queued requests when acquiring/releasing a connection. This is a hypothesis, not yet an attributed root cause. Current evidence cannot distinguish pool bookkeeping from CPU/event-loop scheduling or response-body handling.
- **Decision:** Add opt-in standard-library cProfile execution to each existing generator shard, retaining its schedule, HTTP client, connection/concurrency budget and request protocol. Store raw profiles separately, and emit compact ranked CPU costs plus configuration, revision, strict gates and transport timings. Run a bounded loopback diagnostic before selecting a pool/client replacement. A profiled run is diagnostic evidence only; profiler overhead makes its latency unsuitable for capacity comparisons. Default runs remain unprofiled.
- **Alternatives:** Modify HTTPcore internals before measurement (rejected: changes the behavior being investigated); introduce a third-party sampler (deferred: installation and platform dependencies); enlarge the pool or relax gates (rejected: masks the problem and confounds prior controls).
- **Consequences:** Ranked self-time identifies where generator CPU is spent; cumulative times overlap and must not be summed. Profiles include code paths but no credentials or manifest values. Compact reporting reduces repeated raw-output reads. This augments ADRs 0040 and 0090; it supersedes neither. No real datastore is accessed by the loopback control.
- **Failure/recovery behavior:** Missing shard outputs/profiles or invalid responder timing fail interpretation; retain the strict generator failure. The wrapper cleans up child processes and private manifests. Use fresh output/profile paths. Profile collection never turns a failed generator stage into a pass.
- **Validation evidence:** Planned: focused regression tests, bounded profile smoke and generator-ECS CPU profile. Record executed evidence before drawing conclusions or implementing a changed pool/client pattern.

Executed evidence: ten focused tests passed and changed-script lint passed. The clean `fb99cd6` generator-ECS profile (60/s for 30 seconds, two shards, 500 in flight, same 30 ms/0.5 s/5 s synthetic delays) produced both raw profiles and ranked reports. Responder timing was valid; the generator failed with 589/1,800 drops. Connection assignment ran 38,631/37,385 times, with cumulative elapsed profile time 19.98/20.73 s; connection `is_idle` ran 5.21/6.07 million times. These are profiled elapsed costs, not process CPU percentages: cProfile also records blocking poll time. This identifies pool bookkeeping as a major cost and motivates a bounded-pool experiment; the profiled timing is not a capacity comparison.
