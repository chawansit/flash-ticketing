# 0082 — Test two Kafka consumers for paid-ticket fulfillment

- **Status:** Accepted diagnostic experiment; two consumers were not promoted because the strict gate still failed. One consumer remains the rollback configuration.
- **Context:** On 2026-09-29, a one-consumer, 30 paid-journeys/s stage scheduled 1,800 journeys over 60 seconds. The consumer accumulated about 52 busy seconds during the sampled minute. With an eight-thread development simulator, PAID orders awaiting ticket issuance peaked at 296, and hold-to-ticket p95 was 24.91 seconds. The stage failed from generator drops and API DB-pool 503s. The six-partition Kafka topic has parallelism available, but these measurements do not yet isolate Kafka lag from the consumer's PostgreSQL work. ADR 0052 established a two-consumer experiment for SeatsChanged; this decision extends a controlled comparison to OrderPaid and ticket issuance.
- **Decision:** Run one matching development fixture and 30/s, 60-second workload with two consumers in the same group, keeping four API replicas, API pool maximum three, eight simulator threads, six Kafka partitions, three callback deliveries, status-poll interval and admission unchanged. Count both consumer replicas in worker telemetry and check the PAID-to-FULFILLED backlog, issued-ticket deadline, 503 cause, callback queue and post-TTL audit. Do not increase arrival rate until strict gates pass. Restore one consumer after the stage.
- **Alternatives:** Increase the API pool/waiting queue first would address some 503s but would not isolate ticket-issuance delay. Add more Kafka partitions first is unwarranted while six already exist. Bypass Kafka and issue tickets inside the payment webhook would lengthen the payment transaction and couple API latency to issuance. Mark PAID as a completed sale would violate the target's durable-ticket counting rule.
- **Consequences:** A second consumer adds another process and up to one additional twelve-connection client pool; PgBouncer still caps server connections at its existing value. This comparison does not keep total potential client connections identical, so RDS and PgBouncer pressure must be inspected. More consumers can reveal a downstream database or publisher bottleneck. API pool 503s remain a separate failure gate.
- **Failure and recovery:** Kafka reassigns six partitions if either consumer stops. The durable consumer inbox and idempotent ticket uniqueness handle replay. On any failed gate, stop escalation, audit all accepted orders after the hold TTL, inspect dead letters and queues, and restore the original one-consumer topology and simulator setting.
- **Validation evidence:** The one-consumer baseline and post-TTL audit are in [the API-pool diagnostic](../capacity/flash-sale-opening/paid-ticket-api-pool-2026-09-29.json). The [two-consumer aggregate comparison](../capacity/flash-sale-opening/paid-ticket-two-consumers-2026-09-29.json) records the executed stage. It dispatched all 1,800 scheduled journeys without generator drops, reduced peak PAID orders awaiting tickets from 296 to 9 and hold-to-ticket p95 from 24.91 to 1.11 seconds. Nevertheless, five buyer-visible 503 responses remained, all in a stage that still recorded API DB-pool TooManyRequests. The strict gate failed. Post-TTL audit found 1,799 successful payments and 1,799 unique tickets; one payment-rejected order expired. All 5,397 callback targets completed, queues drained, no duplicate booking was found, and rollback restored one consumer. This supports further evaluation of two consumers but does not certify it as production topology or prove the 300,000-ticket/hour target.
