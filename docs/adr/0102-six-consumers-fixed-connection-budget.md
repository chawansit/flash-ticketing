# 0102 - Six consumers with a controlled connection budget

- **Status:** Accepted on 2026-10-03 before implementation; user Continue authorizes one same 60 buyers/s comparison.
- **Context:** ADR 0101 found offset commits fast (mean2.38ms), uneven partition processing and failed dispatch timing at60/s. Six partitions were assigned to four members; default range reproduction pairs0+1 and2+3, leaving4and5single. Actual ownership and refresh retry SQLSTATE were missing. Live PgBouncer reports transaction pooling, DEFAULT_POOL_SIZE24, reserve0, client limit160; baseline consumers have DB_POOL_MAX12 and execute handlers serially.
- **Decision:** Compare six consumers against four with the same60buyers/s60s/twelve-show fixture and generator lifecycle diagnostics. One consumer can own each existing partition. Keep PgBouncer application server-pool24/reserve0/client160, four API pools3, three reservation writers, simulator8, admission4, polling1s, cache3s and all durable/idempotency/TTL boundaries unchanged. Set consumer pool ceiling8 per replica:6x8=48, equal to the previous4x12 ceiling. Serial handler concurrency increases4to6 (the tested topology factor); idle minimum clients may increase by two, and this is not a claim that global RDS connections are hard-capped24. Add an opt-in consumer pool override to horizontal Compose and bounded runner checks/restoration. Capture credential-free hashed member-to-partition mapping and fixed-allowlist SQLSTATE retry counters. No new retry, async commit, partition count or paid rate change.
- **Alternatives:** Round-robin assignment still gives two workers two partitions with6/4, merely moving which partitions share a worker. Changing generator process count simultaneously confounds attribution. More API workers does not directly resolve consumer service pressure. A smaller batch can improve fairness but may increase refresh transactions and does not add processing capacity.
- **Consequences:** Six serial consumers may use more of the existing24-connection application server pool and compete with API/simulator work; the same aggregate consumer client ceiling limits idle growth but does not make active concurrency identical. Database waits/latency and generator delay remain measured gates. Member fingerprints disclose no original IDs/hosts, and summary reports group layout. Diagnostic counters report attempts including recovered failures, not customer failures.
- **Failure/recovery behavior:** Preflight must confirm baseline consumer pool12, candidate6x8 and unchanged PgBouncer budget before load. Abort on mismatch; restore baseline one consumer/pool12 and all original service settings/cache0. Stop after this bounded control on customer/generator failure; never mask it with caller retries. Preserve exact post-TTL accepted-payment ticket/zero-double-booking/queue/Kafka audits, fixture retirement and source coherence. Existing inbox/outbox, bounded batch retry/backoff, partition rewind and synchronous commit semantics remain unchanged. Do not infer payment failure from a failed read.
- **Validation evidence:** Executed locally: all 362 unit/integration tests passed in 61.89s; 19 focused layout/budget/observer/retry checks and changed-file lint passed. Live budget/ownership checks and same-rate comparison are pending against [ADR0101diagnostic](../capacity/flash-sale-opening/paid-consumer-phase-diagnostic-2026-10-03.json). No result claimed before execution. This accepts an experimental topology only, not a permanent production scaling decision. Existing accepted delivery/idempotency/TTL decisions are not superseded; six-consumer scope extends ADR0101validation.

## Executed control

The [same 60 buyers/s control](../capacity/flash-sale-opening/paid-six-consumer-control-2026-10-03.json) at e803575 confirmed six singleton partition owners and a fixed consumer client ceiling of 48, with PgBouncer application pool 24. Kafka peak lag fell from 1,192 to 54; backend callback-to-ticket p95 fell from 8.865 s to 260 ms; customer hold-to-ticket p95 fell from 13.679 s to 7.972 s. Generator drops fell from two to zero and dispatch p95 to 24 ms. The strict customer gate **failed**: seven order-status GET 503s plus five payment POST 503s, or 12/3,600 journeys (0.333%). API metrics recorded 13 pool TooManyRequests failures; three seat-refresh attempts failed with SQLSTATE 55P03 and recovered. Payment-due-to-callback p95 rose from 1.031 s to 5.150 s, now a material remaining delay. No rate escalation ran.

The initial all-paid audit failed. A fresh post-TTL audit of the independently database-proven cohort passed: exactly 3,595 paid tickets plus five unpaid expired orders, zero double bookings and empty queues/Kafka. Changing the audit cohort does not turn the customer gate into a pass. The original one consumer/pool 12, service budgets, cache disabled, readiness and all seven source hashes were verified after restoration. All 362 local tests passed in 61.89 s; 19 focused checks and lint passed. Six consumers remain an experimental result; no permanent production promotion. Next proposal is a separate same-rate API pool 3-to-4 control with application server pool 24 fixed, before any rate escalation.
