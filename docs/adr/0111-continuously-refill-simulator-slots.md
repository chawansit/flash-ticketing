# 0111 - Continuously refill bounded development callback slots

- **Status:** Accepted for a controlled experiment before implementation on2026-10-03; production promotion pending evidence.
- **Context:** simulate_batch submits eight tasks then waits for all eight before refilling any slot. Code inspection establishes a barrier, not its quantitative contribution to the failed cloud stage. Slow HTTP/DB tasks can park completed slots. The simulator is development-only and cannot certify real provider throughput.
- **Decision:** Add an opt-in refill scheduler alongside default batch mode. Keep at most configured slots outstanding, reuse the same executor and independently replenish completed slots. Back off each empty/error slot100ms, stop scheduling promptly on shutdown and drain existing work. Keep eight slots/pool12 for the candidate, identical HTTP transport/timeout, claim/ack SQL,15s lease, stable callback IDs and token-fenced acknowledgement. Bound per-slot state by concurrency; no unbounded executor queue. Select mode through validated simulator configuration and the existing stage runner; restore batch mode/concurrency4 after each arm. This supersedes only the experimental batch scheduling choice in ADR0081; persistence/idempotency/TTL/Kafka semantics remain unchanged.
- **Alternatives:** More threads increases concurrency and can hide inefficient scheduling. Async HTTP/reusable connections simultaneously changes transport. Removing leases or fencing compromises crash/replay safety. Changing production webhook routing is a separate experiment.
- **Consequences:** Refilling may increase actual downstream HTTP/DB pressure even with the same slot ceiling. Independent100ms empty/error backoff prevents hot idle loops but changes idle-slot scheduling intentionally. Benchmark generator remains two processes,total60buyers/s500active500HTTPconnections16clients,300s/60shows18000actors,poll1s,one callback and no caller retry. Backend remains4API/pool4/admission4/waiters12/cache3s,6consumers/pool8,3writers/batch4/maxage60,simulator8/pool12,PgBouncer24/reserve0/client160.
- **Failure/recovery behavior:** Test a straggler, empty queue, errors and shutdown; no new work after stop and no more than configured active/outstanding tasks. Existing lease expiry handles failed delivery, stable IDs handle lost acknowledgements, token fencing prevents stale owner updates. Do not add HTTP retries. Stop rate progression on failed gates; retire fixtures, audit paid/unpaid/TTL/zero doublebooking/full queues/Kafka and restore baseline/source/readiness/idle/private scratch. Financial or evidence failures in the instrumented baseline prevent candidate load.
- **Validation evidence:** Pending deterministic straggler and bounded scheduler tests, phase parsing/reset/privacy coverage and appropriate full unit/integration suite. One instrumented batch control and one same-rate refill comparison are authorized by the approved plan, conditionally on correctness/monitoring gates.
