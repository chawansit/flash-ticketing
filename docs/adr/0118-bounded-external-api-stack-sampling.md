# 0118 - Bounded external API stack sampling

- **Status:** Accepted for diagnostic implementation on 2026-10-03; application optimization not selected.
- **Context:** ADR0117's same60buyers/s300s control reduced mean poolwait30.37percent but confirmed purchases fell10.41percent,callback delivery grew25.45percent and APIevent-loop delay grew63.88percent. HostCPU averaged97.15percent;APIcontainers consumed1.9792cores. Cgroup counters identify the largest role but not hot functions. Python synchronous handlers and webhook offload already exist; guessing a scheduling/cache change is not justified.
- **Decision:** Add a host-side read-only py-spy sampler and compact speedscope summarizer. Install the profiler in an isolated host tool virtual environment; record actual version and CLI capabilities. Resolve exactly four running API container host PIDs and verify uvicorn command identity before attachment. Sample the four processes at25Hz for120seconds with GIL-only, nonblocking reads, no locals/native capture or process launch/injection. Store private speedscope traces, bounded errors and profiler CPU counters. Aggregate only Python stack observations and bounded route/category/function symbols; omit credentials, locals, request bodies, IDs and private paths from public summaries. Reuse the existing paid runner unchanged at8refill slots/60buyers per second/300seconds with the same admission/pool/cache/consumer/generator budgets and all financial/queue/source/restoration gates. Retain common-helper code61e6c27 for attribution; no new application factor and no higher-rate stage.
- **Alternatives:** In-process cProfile/per-request timers change hot request execution; full native/perf sampling has broader overhead/symbol scope; blindly increase threads/connections/cache age/instances can worsen contention or weaken freshness. Deferred until evidence justifies an ADR and separate candidate.
- **Consequences:** GIL-only samples reveal active Python execution, not exact charged CPU, native Rust/C extensions, GIL-released waits or per-request latency. Nonblocking sampling can produce incomplete/inconsistent stacks. Samples in generic framework code may lack route identity; retain an unattributed category rather than guessing. Sampling overhead on the saturated host is a confound: measure profiler CPU and label the replay diagnostic, not an uninstrumented production-capacity comparison.
- **Failure/recovery behavior:** Reject missing/replaced/mismatched targets, unsupported flags, malformed/empty profiles or collector errors. Hard-bound attachment duration and parent deadlines; terminate/reap owned profiler processes on failure. Do not change ptrace/kernel/container security settings. A failed probe remains failed. Stop sampling before configuration restoration; clean only owned transient profiler files/processes after copying raw evidence. Keep exact paid/unpaid postTTL, zero double booking, full-keyspace queue/Kafka/source/readiness/restoredsettings/generatoridle/private cleanup gates. Diagnose collection failure separately from backend correctness; no retries of customer load.
- **Validation evidence:** Planned unit checks for speedscope indices/weights/orientation/route attribution and malformed/empty input; no-buyer bounded attachment/cleanup smoke against an isolated synthetic Python process; same-load live diagnostic with all final gates.
