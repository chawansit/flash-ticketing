# 0101 - Consumer phase and paid-generator diagnostics

- **Status:** Accepted on 2026-10-03 before implementation. User Continue authorizes narrowly scoped instrumentation and one same 60 buyers/s diagnostic after tests pass.
- **Context:** ADR 0100 failed with 24 active-cap drops, one order GET503, dispatch p95 4.71 s, callback-to-ticket p95 9.734 s and Kafka lag 1,258. All 3,576 dispatched purchases passed exact post-TTL ticket/uniqueness/queue audits. Existing handler busy time omits Kafka polling and offset-commit waits; generator CPU/event-loop measurements already exist behind an optional diagnostic flag.
- **Decision:** Add bounded Prometheus histograms for consumer poll, per-partition processing, offset commit, rewind and fixed event kinds. Observe success/error wall time without changing the existing poll timeout, batch size, durable handlers, seek behavior or synchronous offset commit. Partition labels are limited to 0..31 and other; event labels are a fixed allowlist. Export aggregate deltas and histogram p95 upper bounds through the existing paid observer. Expose the existing single-process generator lifecycle diagnostics through the bounded runner. Repeat one 60 buyers/s, 60-second, twelve-show fixture with the ADR 0100 configuration and no caller retries. No rate escalation or production optimization is included.
- **Alternatives:** Changing commit frequency, consumer concurrency or polling before timing them would confound attribution and alter recovery semantics. Host CPU sampled after load cannot establish generator saturation during load. Reusing existing generator diagnostics avoids an additional process monitor.
- **Consequences:** Metrics add small timing/scraping overhead. Phase wall time is not CPU time; poll time can include healthy idle waiting. Handler/event and partition durations are nested and must not be added. Histogram upper bounds are not exact p95; missing/reset counters must be explicit. Diagnostic mode can perturb the generator, so compare with the earlier same-profile run with that limitation.
- **Failure/recovery behavior:** Preserve all partition start offsets and rewind on handler failure; commit only after every returned partition is handled successfully, as before. A commit failure must propagate, never count as an acknowledged message. No payload/actor/DSN labels. Stop at any failed customer gate, audit exact backend payments after all hold deadlines, ensure zero double booking and drained queues/Kafka, retire fixtures and restore baseline/cache0. Do not infer unpaid status from an ambiguous customer read.
- **Validation evidence:** Planned before cloud: tests for commit-after-all-partitions, all-partition rewind/no commit on handler failure, propagated commit failure, bounded labels/error timings and correct aggregate counter/histogram deltas. Execute existing integration correctness tests; report actual results. Cloud diagnostic will record exact source/configuration and distinguish measured from unresolved phases. ADR 0100 is baseline evidence; no persistence, idempotency, TTL, delivery or scaling ADR is superseded. Extending paid-stage progression remains future scope; this only adds measurements to one existing bounded run.

Local validation executed: all 358 unit/integration tests passed in 66.65 seconds on isolated PostgreSQL17.6 and Redis7.4.5; dedicated test containers removed. Eleven focused consumer/recovery/metric checks passed after the final summary cleanup; lint passed. Cloud diagnostic remains pending.
