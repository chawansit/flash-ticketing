# ADR0193: Bounded atomic payment claim comparison

## Status
Accepted for implementation and local qualification under ADR0172. Extends ADR0189 and ADR0192 into one fresh registered comparison. Registration and cloud execution require executed local qualification and immutable image proofs. No production adoption or superseding financial decision.

## Context
The fresh 60 journeys/s control passed 18,000 paid-and-issued journeys, post-TTL financial reconciliation, queue drain and restoration. Primary CPU pressure, recovered internal callback pool timeouts and intermittent commit latency remain observed. ADR0192 exported only the approved atomic claim into the frozen source and passed native database tests. Its performance on Huawei has not been measured. Existing registered profiles accept one common source/image receipt, so using the candidate through one of those profiles would misidentify the arm or silently change its control.

## Decision
Add a separate atomic_payment_claim profile to the standing registry. Bind both arm-specific full source maps and immutable image receipts in one experiment identity. Control uses the exact passing ADR0171/ADR0163 images and source; candidate uses the source-pinned ADR0192 export. All candidate role images retain their original per-role parent layers and configuration. Only the workers module's claim constant and simulate_one implementation differ; delivery, acknowledgement and every other module remain pinned. No runtime feature flag is added.

Keep 2+2 APIs, aggregate PgBouncer budget 24, API/payment pools and waiter limits, simulator concurrency, cache, polling and all financial/customer gates unchanged. Offer 60 journeys/s for 300 seconds per measured arm. Qualification verifies each actual arm's source, readiness, 100-way same-seat safety, replay, authorization, payment durability after TTL, queue drain and restoration. A failed qualification or measured control stops progression. Require both arm results, including customer completions, CPU, database/pipeline phases and failures, before concluding improvement. Preserve an inconclusive or negative outcome.

Reuse the existing guarded image staging before qualification within the fresh registered reservation, loading the union of arm images into existing caches without deploying services. Verify all local images before upload, fresh owned archive paths, exact transfers, unchanged runtime identities, idle generator and archive cleanup. Retain the existing 3 GiB archive ceiling. For the pair, conservatively count unique verified parent roots plus each overlay, rather than counting the same inherited roots twice; verify actual archive size and SHA before transfer. Bind staging helpers, exporter, parent source helpers and the exact plan in the runner identity. Guard every cloud call and retain ambiguous ownership failures. Use new_stage_output() for staging directories. Existing profiles retain their default single-receipt behavior.

The 3,600-second reservation covers staging, both qualifications and both matched measured windows; mandatory owned cleanup may exceed it. The 300-second workload is the shortest existing qualified window suitable for a fair baseline/candidate comparison. No hourly or higher-load stage is added. After both pass, compare results before adoption or a separately registered load increase.

## Alternatives
Reuse a historical scope or relabel a placement profile: rejected. Replace the control with the latest checkout: rejected. Add a runtime feature flag: avoids separate image receipts but adds unnecessary deployment behavior. Change pools or service placement alongside SQL: confounds attribution. Skip a safety, post-TTL or restoration check: rejected.

## Consequences
The registry gains one explicitly bounded pair and arm-aware source verification. Image staging adds local build/transfer cost but does not change resource sizes or spend. Both arms share the same benchmark scaffolding and diagnostics; only qualified application bytes differ. Passing customer/correctness gates alone does not establish meaningful improvement or 300,000 tickets/hour.

## Failure and recovery behavior
Reject unknown profiles, incomplete or swapped receipts, extra source changes, changed settings, stale qualification, pauses, old scopes, changed image parents, archive/source tampering and budget drift before dispatch. Preserve failed evidence and consumed counters. A failed control prevents candidate load. Uncertain staging ownership, financial reconciliation or restoration blocks new load; the historical ADR0190 exception is limited to its original run. Never use retry to alter this comparison's customer validation.

## Executed cloud result
Fresh registered scope bounded_atomic_payment_claim__117aded48607 completed in 2,658.766 seconds (44.31 minutes), within its 3,600-second ceiling. Both safety arms and both measured 60 journeys/s, 300-second arms passed all gates and restored the original services. Each measured arm reconciled 18,000 paid-and-issued tickets, zero customer errors/drops/retries, zero duplicate booking/payment loss and complete global/Kafka drain.

Claim mean fell 9.2467 to 8.6418 ms (6.54%); hold-to-ticket worst-shard p95 fell 1,835.59 to 1,667.60 ms (9.15%). Primary offered-window CPU stayed effectively unchanged (70.7070 to 70.6076%). Payment HTTP p95 rose 4.90%, simulator delivery mean rose 18.32%, and internal transient failures still occurred and recovered. This is a mixed latency result from one sequential pair, without demonstrated higher capacity or hourly qualification. Keep the normal deployment restored; target measured background CPU imbalance next, with unchanged total budgets.
