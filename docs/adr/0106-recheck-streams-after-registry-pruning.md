# 0106 - Recheck event streams after advisory registry pruning

- **Status:** Accepted on 2026-10-03 before implementation. Local correctness repair; no cloud load or permanent promotion authorized by this ADR.
- **Context:** The five-minute ADR 0104 attempt left one accepted command in a nonempty event stream absent from the advisory registry, with group pending=0/lag=1 and no PostgreSQL command. Its historical cause cannot be reconstructed. A deterministic real Redis/PostgreSQL regression at local HEAD 886c31a now reproduces a sufficient mechanism: writer XLEN returns zero, enqueue atomically writes XADD and subsequently succeeds at registry SADD, then the writer's stale SREM removes that new pointer. With fallback scanning disabled, the regression fails at registry membership (1 failed in 2.51 s). The separate registry-write failure path remains possible.
- **Decision:** Retain bounded fair stream windows and existing discovery cadences. After best-effort SREM of initially empty candidates, pipeline a second XLEN over only those candidates. Put newly nonempty streams in the current polling window and restore their registry pointers using SADD. If the second read fails, conservatively retain and re-register all uncertain candidates. If registry restoration fails, keep those candidates locally eligible and record registry_error; retain existing reset and incremental SCAN recovery. This explicitly supersedes ADR 0066's stale-length-only compaction and ADR 0067's preservation of that compaction; their other bounds/cadences remain accepted. Redis intake Lua, per-event hash tags, replica acknowledgement, persistence/idempotency/locking, hold TTL and Kafka semantics are unchanged.
- **Alternatives:** A multi-key Lua script combining XLEN with global registry SREM crosses event hash slots and would violate the accepted Cluster slot layout. A global stream changes contention, routing and ordering. Disabling all pruning grows historical registry work indefinitely. Accelerating whole-keyspace SCAN adds idle traffic and only reduces the recovery delay; it does not remove the race. Registration generations or a durable discovery queue require new metadata/retention and broader changes.
- **Consequences:** Removal-before-recheck ensures that a concurrent successful enqueue either appears in the second length read and is re-registered, or performs its own SADD after the removal. Multiple healthy pruners satisfy the same ordering. An enqueue after the second zero read remains registered and is found on the next ordinary refresh. Work is bounded by the existing candidate window; empty candidates add one pipeline round trip, and only revived/uncertain candidates add a registry write. No cross-slot atomic operation is introduced; this does not certify full Redis Cluster client support.
- **Failure/recovery behavior:** Never acknowledge/delete commands during discovery. PostgreSQL commit and existing replay-safe writer acknowledgement remain required. A second-read error retains uncertain streams rather than silently discarding them, and attempts one bounded conservative registration. A failed registry write is still advisory; commands remain in Redis and can be discovered locally or by existing SCAN after restart/reset. Redis outages, lost writes and enormous namespaces still have no new TTL-bounded discovery guarantee; do not claim all missing-pointer mechanisms fixed. Keep full keyspace queue audits independent of the registry, exact paid/post-TTL/zero-double-booking gates and baseline restoration. Rollback changes discovery code only, with no schema migration.
- **Validation evidence:** Pre-fix regression executed and failed as described above, raw local evidence in ignored tmp/registry-race-reproduction.txt. Post-fix concurrency, advisory write/read failure, bounded rotation, replay/durability and full unit/integration validation are required and will be recorded after execution. No new cloud capacity measurement has run.


Executed validation: the repaired real Redis/PostgreSQL regression passes for enqueue immediately before and after SREM, commits exactly one command/order and drains XLEN/XPENDING to zero. Advisory SADD failure accepts the command and a bounded scan in the isolated namespace persists it replay-safely. Unit cases cover remove/read/restore errors, enqueue after the second zero read, fairness and hard read-count bounds (18 focused tests passed in 0.45 s). The first full suite found the independent expiry race, recorded in ADR 0107. After that repair, the final full unit/integration suite passed 376 tests in 66.84 s with two existing dependency deprecation warnings. Changed-file Ruff, Python compilation and git diff --check passed. Dedicated local PostgreSQL 17.6 / Redis 7.4.5 containers were removed by the harness. Cloud deployment/performance/retest remain unexecuted. See [compact repair evidence](../capacity/flash-sale-opening/registry-expiry-correctness-2026-10-03.json).
