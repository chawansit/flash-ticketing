# 0092 - Partition synthetic generator HTTP pools with a fixed total budget

- **Status:** Accepted for a bounded experiment; production application unchanged.
- **Context:** ADR 0091 identifies HTTPcore connection assignment and millions of connection-state checks as major profiled costs. An unprofiled single-client-per-shard control dropped 394/3,600 journeys despite a healthy loopback responder. More total connections and slower polling previously failed; changing the total load/budget would confound attribution.
- **Decision:** Add an opt-in HTTP-client count, default one, to the existing paid generator. Test eight independent HTTPX clients per process on the same two-process generator. Partition each process's 250-connection budget exactly across eight pools (32/32/31/31/31/31/31/31), retain a global 250 active-journey cap, and assign each journey to one client by its scheduled index for its entire lifecycle. Keep 60 journeys/s for 60 seconds, 0.2 s polling, one callback, no retries and the same responder delays. Report pool budgets/client count. A strict pass still requires every scheduled journey fulfilled by deadline, no drops/errors/duplicates and acceptable dispatch lag; a synthetic pass is not a durability or backend capacity result.
- **Alternatives:** Replace HTTPX with another client (deferred until a controlled comparison); patch HTTPcore internals (rejected for now due maintenance and behavior risks); increase connection/concurrency budgets (rejected: changes the experiment and may hide delays); add processes/machines (deferred: changes resource allocation).
- **Consequences:** Smaller independent pools reduce per-pool scans while preserving total connection headroom. HTTPX stays unchanged. Pools retain independent idle connections and may be unevenly occupied; no per-pool load balancing is claimed. Aggregate transport timings remain worst-shard p95. The default remains one client. This augments ADRs 0087 and 0090 and does not supersede production decisions.
- **Failure/recovery behavior:** Reject invalid client counts or budgets before any request. Close every client on normal exit, startup failure or cancellation; retain global generator drop accounting. If responder or generator gates fail, retain evidence and do not promote the candidate or attribute backend capacity. Preserve exact post-TTL audits/queue drain if later testing against the backend. Stop at a failed stage.
- **Validation evidence:** Planned: regression tests for global cap/total budget/client cleanup, then an unprofiled same-profile loopback comparison. Only after a valid zero-drop control may the candidate be used in a real paid stage.
