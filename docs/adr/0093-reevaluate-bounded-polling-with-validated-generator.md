# 0093 - Re-evaluate bounded polling after validating the generator

- **Status:** Accepted for a controlled workload experiment; production client cadence undecided.
- **Context:** The fixed-budget client option passed the synthetic control and dispatched all 2,700 buyers at real 45/s, but order GETs returned 2,111 HTTP 503s and payment POSTs 304. API metrics show 2,814 TooManyRequests pool rejections and two PoolTimeouts, full three-connection pools with twelve waiters, and mean connection occupancy 34.54 ms. Order polls issued 30,452 GETs while Kafka lag peaked at 98 and drained. Post-TTL exact audit confirmed 2,396 accepted payments/tickets, 304 expired unpaid orders, no duplicate bookings and empty queues. Faster generator dispatch exposes real DB pressure. ADR 0088's earlier slow-poll experiment still had generator drops and cannot resolve the behavior with this corrected generator.
- **Decision:** Reuse ADR 0088's bounded 1.0-second command/order polling experiment with the corrected generator. Begin at the same 45/s, 60 seconds, one process/eight HTTP clients, 500 total connections/concurrent buyers, nine shows, one callback, no retries and identical backend settings. Change only polling from 0.2 to 1.0 seconds. Capture customer completion, physical GETs, pool errors, callback backlog, latency, exact post-TTL integrity, queue drain and rollback. Only if this control passes may a bounded 60/s two-shard stage run at the explicitly changed read:write mix. This does not increase intrinsic backend capacity or define a production SLA.
- **Alternatives:** Increase DB connections/waiters (deferred: changes resource budgets before reducing avoidable work); build a Redis order-state projection or push channel (deferred pending a consistency/recovery ADR); repeat identical overloaded load or add retries (rejected: no new attribution or hidden failures).
- **Consequences:** Less polling may protect payment/callback DB access but adds up to approximately 0.8 seconds of status observation delay per phase. Each journey still consumes one durable payment and one issued ticket. Compare offered journeys separately from physical HTTP RPS. The earlier 0.2-second result remains failed; eventual fulfillment does not imply a successful customer journey. This augments ADRs 0088 and 0092 without promoting or superseding production patterns.
- **Failure/recovery behavior:** Stop escalation on any generator, unexpected-response, deadline, integrity or queue failure. Retire only the isolated fixture and always restore baseline services. After payment rejection, audit accepted payment count independently of total dispatched buyers and wait through hold TTL before expecting unpaid orders to expire. Do not conceal the failed stage by correcting the audit expectation.
- **Validation evidence:** [Failed real control](../capacity/flash-sale-opening/real-paid-partitioned-control-2026-10-03.json); corrected post-TTL audit and queues passed, rollback passed. The opt-in client implementation passed 212 unit tests. A separate observed Windows subprocess decode defect was fixed with explicit UTF-8 and replacement of malformed log bytes; 19 transport/orchestration tests passed. The 1.0-second candidate has not yet run.
