# 0103 - Four API pool connections with a fixed server budget

- **Status:** Accepted on 2026-10-03 before implementation. User Continue authorizes one same-rate comparison.
- **Context:** The ADR 0102 six-consumer control eliminated generator drops and reduced callback-to-ticket p95 to 260 ms, but 12 of 3,600 journeys received HTTP 503. API metrics recorded 13 TooManyRequests pool acquisition failures. Four API replicas each had pool maximum 3 and at most 12 queued waiters. Callback due-to-delivery p95 increased to 5.15 s. More active consumers can compete for the shared database pool even when aggregate client ceilings stay fixed.
- **Decision:** Run one 60 buyers/s, 60-second comparison with API pool maximum 4 per replica rather than 3. Keep four API replicas, admission 4, waiter cap 12, six consumers with pool 8, PgBouncer application server pool 24/reserve 0/client limit 160, three reservation writers/batch 4, simulator concurrency 8, order cache 3 seconds, and the same single-process generator/500 connections/16 clients/one-second polling. The aggregate API client ceiling increases from 12 to 16; the PgBouncer application server budget does not increase. Expose a bounded opt-in runner flag using the existing Compose environment knob. Check actual API pools before deployment, after deployment and after restoration. Report the effective pool size rather than a hard-coded value.
- **Alternatives:** Increasing the waiter limit or timeout stores more latency without adding service capacity. Caller retries would obscure first-attempt errors and change offered work. Increasing PgBouncer or RDS resources simultaneously would prevent attribution. Query reduction and callback-worker fairness may help later, but require separate evidence and decisions.
- **Consequences:** API bursts may acquire connections without overflowing the bounded waiting queue. More API clients can instead increase shared-pool contention and delay callbacks or consumers. This is a hypothesis, not a guaranteed error fix. PgBouncer DEFAULT_POOL_SIZE is per database/user pool, not a global RDS connection cap. The reference report is [ADR 0102 control](../capacity/flash-sale-opening/paid-six-consumer-control-2026-10-03.json).
- **Failure/recovery behavior:** Require the original four API pools of 3 and the existing consumer/PgBouncer budgets. Abort before load on any mismatch. Restore API pools to 3, waiter caps to 3, cache disabled, one consumer/pool 12 and other original service settings; verify readiness and source coherence. Stop after this single control if any customer or correctness gate fails. Preserve original hold deadlines and audit exact backend-proven paid tickets plus expired unpaid orders, zero double booking, and drained queues/Kafka. Do not infer lost payment from a failed client status read. No new retry, persistence, locking, TTL or message semantics are introduced.
- **Validation evidence:** Executed locally: 24 focused budget/orchestration tests passed in 3.79 s; changed-file lint, normalized-LF POSIX shell syntax and Compose candidate mapping checks passed. Live pool/ownership verification, customer and callback metrics, exact post-TTL audit and restoration are pending. The existing 362-test application suite passed before this orchestration-only change; do not claim it was rerun. This decision extends experimental validation, does not supersede accepted durability/idempotency decisions, and does not promote six consumers or four-connection API pools permanently.

## Executed control

The [same 60 buyers/s control](../capacity/flash-sale-opening/paid-api-pool-four-control-2026-10-03.json), run checkout-20261003T062430Z-9a3bc1 at ef42cb6, passed all 3,600 paid customer journeys with zero customer errors, generator drops or caller retries. Actual API pools were four per replica, consumers six with pool eight, and PgBouncer application server pool 24 unchanged. API pool failures fell from 13 to zero; successful acquisition mean fell from 11.32 to 2.84 ms. Hold-to-ticket p95 fell from 7.97 to 4.48 seconds. Callback due-to-delivery p95 fell from 5.15 seconds to 678 ms; callback-to-ticket p95 was 306 ms. Three recovered seat-refresh lock-timeout attempts remain; zero customer errors does not mean zero internal retries.

Fresh post-TTL audits passed exact 3,600 paid tickets, zero double booking/extra paid events, no dead letters and empty queues/Kafka. Actual original API pools of three, one consumer/pool 12, other settings/cache disabled, readiness and all seven application source hashes were restored and verified. All application source hashes match ADR 0102; only orchestration/configuration varied. Local validation was 24 focused tests in 3.79 seconds plus lint, POSIX syntax and Compose mapping checks; the earlier 362-test application suite was not rerun for this orchestration-only change. This one-minute customer gate does not certify every latency SLO, sustained hourly capacity or permanent production settings. Next proposal is a longer same-rate validation before rate escalation.
