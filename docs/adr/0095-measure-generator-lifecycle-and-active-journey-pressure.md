# 0095 - Measure generator lifecycle and active-journey pressure

- **Status:** Accepted for diagnostic tooling only; production architecture unchanged.
- **Context:** The 45/s controls label all capacity-cap drops as generator drops. The implementation drops only when its active-journey cap is full; a 500 cap at 45/s has an approximately 11.11 s steady-state average residence-time budget. Slow backend fulfillment and client overhead can both exceed it. Existing transport hooks stop at response headers, omitting body consumption and pool release. HTTPcore response_closed.complete precedes PoolByteStream removal/reassignment, so it alone cannot measure release work.
- **Decision:** Add opt-in lifecycle diagnostics to the existing generator and propagate them through the two-shard synthetic runner. Wrap the public HTTPX AsyncByteStream without pre-reading it or changing request/poll behavior; measure body completion, stream-close work including the underlying pool release, and request-to-close timing. Add bounded event-loop lag/process CPU measurements, actual journey durations for every outcome, active-journey peak/time-weighted occupancy, explicit capacity-cap drop reason and at most eight drop snapshots. Preserve existing load, connection, timeout, retry and strict-gate behavior. Run the established 60/s, 500-cap, 30 ms-response, 0.5 s-durability, 5 s-ticket synthetic control, followed by its already-approved 20 s-ticket saturation control only if the responder remains valid.
- **Alternatives:** Infer pool/body delays from response headers (insufficient); raise caps or add retries (changes workload/masks backpressure); patch HTTPcore internals (unnecessary maintenance risk); attribute cap drops solely to client scheduling (unsupported). A separate one-process 45/s reproduction is deferred; two-shard controls are not exact replicas of that real stage.
- **Consequences:** Diagnostic tracing adds overhead, so comparisons must identify enabled instrumentation and cannot claim a performance improvement from these runs. Global active-journey limit remains separate from HTTP-connection limits. Aggregated shard percentiles remain worst-shard values, and peak occupancies are reported per shard rather than claiming coincident global peaks. No credentials, URLs, bodies or actor identifiers are recorded. Synthetic evidence cannot validate database durability, seat uniqueness or production capacity.
- **Failure/recovery behavior:** Missing trace events remain absent sample counts, never fabricated zero samples. Underlying streams close on errors/cancellation and wrappers preserve exceptions. Close observers/child processes/connections on exit and remove temporary manifests. Any intentional saturation failure stays a failed strict gate; valid responder timing is required before causal interpretation. No real API load or production configuration changes in this experiment.
- **Validation evidence:** Executed:18 focused tests passed, including real HTTP lifecycle/connection cleanup and body/close failures; full unit suite220 passed; changed-file lint passed. Clean-revision generator-ECS controls remain pending. Record executed results and limitations before drawing conclusions. Builds on ADR0090/0092 without superseding production decisions.
