# 0083 — Decouple bounded API DB-pool waiters from connection count

- **Status:** Accepted for an opt-in diagnostic implementation; the higher waiter cap is not promoted to deployment.
- **Context:** The 2026-09-29 two-consumer paid-ticket stage dispatched all 1,800 scheduled journeys and reduced peak PAID-to-ticket backlog to nine, but five buyer-visible checkout requests returned 503. Per-replica metrics recorded twelve DB-pool TooManyRequests failures. Each of four API replicas had three DB connections, at most three requests waiting, and a 500 ms pool acquisition timeout. TooManyRequests rejects immediately when the bounded waiter list is full; this is distinct from a timeout, database lock wait or payment failure. Raising DB connection count would change PgBouncer/RDS concurrency and does not isolate the immediate rejection mechanism.
- **Decision:** Make maximum DB-pool waiters an explicit, bounded API setting. Its default equals the existing per-replica connection maximum, preserving current behavior. In one controlled experiment, permit twelve waiters per API while keeping three connections, the existing 500 ms acquisition timeout, four API replicas, two consumers, simulator setting and 30/s paid journey workload fixed. Record TooManyRequests, PoolTimeout, checkout latency, pool waiters, generator drops, paid-to-ticket latency and post-TTL integrity. A lower 503 count alone is insufficient if latency, throughput or queue drain worsen.
- **Alternatives:** Raise API DB connections first would increase RDS concurrency and hide whether admission is the issue. Unlimited waiting risks unbounded latency and memory. Application-level retries can mask first-attempt failures and duplicate ambiguous payment operations. A Redis order-status projection or push notifications could reduce polling demand, but requires a separate consistency and recovery decision.
- **Consequences:** Extra waiting requests occupy API worker capacity without raising database transaction concurrency. Under sustained overload they may time out at 500 ms and raise tail latency. The cap must remain bounded and metrics must distinguish immediate rejection from timeout. The setting is API-only; background workers keep their current default.
- **Failure and recovery:** If the candidate raises p95 latency, creates PoolTimeout, drops scheduled buyers, leaves PAID orders unfulfilled, or fails any strict integrity or rollback gate, restore the original waiter cap of three and one-consumer deployment. Existing PostgreSQL uniqueness, callback idempotency and Kafka inbox remain the correctness boundaries. A request that already committed payment but lost its response is resolved by the same idempotency key and durable order audit.
- **Validation evidence:** The failed two-consumer baseline and post-TTL audit are in [the redacted comparison](../capacity/flash-sale-opening/paid-ticket-two-consumers-2026-09-29.json). The opt-in configuration requires unit tests and a cloud A/B stage before any deployment decision; no higher-capacity claim is made here.
