# 0109 - Compare two paid generator processes at fixed total budgets

- **Status:** Accepted on 2026-10-03 before implementation. User Continue authorizes one bounded cloud comparison, with no rate escalation or permanent topology promotion.
- **Context:** The source-consistent single-process control at1950606 scheduled18,000 buyers at60/s over300s, dispatched17,695 and dropped305 at500 active journeys. Three HTTP503s matched API pool rejections. Generator CPU averaged0.899 core and dispatch p95 was3081ms; these observations suggest client pressure but do not prove a sole bottleneck. The existing sharded generator already forwards lifecycle diagnostics to both children and retains their results. Only the checkout runner rejects diagnostics with two shards; the previous checkpoint's implication that propagation was missing is corrected by inspection.
- **Decision:** Permit the runner's existing diagnostics option for either supported paid generator layout, while retaining rejection for a nonpaid run. Execute one comparison against checkout-20261003T092412Z-1e53e2 with two synchronized processes, each30 buyers/s,250 active journeys,250 HTTP connections and8 HTTP clients: totals remain60/s,500 active,500 connections and16 clients. Retain300s,60 isolated300-seat shows,18,000 actors, one-second polling, one callback delivery and zero caller retries. Preserve all backend settings from ADR0104/0108: four APIs/pool4/admission4/waiters12/cache3s, six consumers/pool8, PgBouncer application pool24/reserve0/client160, three writers/batch4/max command age60s and simulator8. Use existing per-child diagnostics and worst-shard percentile summaries; do not average child percentiles or label them a combined p95. Anchor approximate observer windows to the earliest child start and report start skew separately. No generator request or application behavior changes.
- **Alternatives:** Increasing connections, concurrency, rate or backend pools confounds generator isolation with capacity. Rewriting the generator discards the identified baseline. Removing diagnostics loses evidence of each process's pressure. A synthetic loopback test under ADR0090 cannot certify backend durability or paid-ticket capacity.
- **Consequences:** Process layout and client placement change together while total budgets stay fixed; show subsets necessarily become disjoint per child. Fresh fixture identities and backend history remain uncontrolled across runs. The result can compare this profile, not establish a universal production limit or300,000 tickets/hour. Existing sharded diagnostics are reused, not claimed as newly implemented.
- **Failure/recovery behavior:** Require equal checkout revisions, matching deployed source modules including simulator, readiness, fixture validity and observer startup before dispatch. Preserve every dispatch/drop/HTTP/customer latency gate. Stop progression after the single authorized stage, including on failure. Separately audit exact paid and unpaid cohorts, all original hold deadlines, zero duplicate bookings/extra paid events, full-keyspace queues and Kafka drain. Retire fixture, terminate parent and child generators, remove private scratch and restore the original four APIs/pool3/waiters3/cache0, one consumer/pool12, simulator4 and baseline worker roles. Preserve failed customer verdicts even when backend audits pass. Authorized temporary SSH access remains only for continued cloud work.
