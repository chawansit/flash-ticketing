# 0108 - Include payment simulator in deployment source consistency

- **Status:** Accepted on 2026-10-03 before implementation. Deployment repair only; no additional load stage authorized.
- **Context:** The same60buyers/s300s revalidation at c2e0f5f dispatched17950of18000 buyers, dropped50 at its500-active limit and fulfilled all17950 without HTTP errors/caller retries. During measurement, source checks on the simulator found workers.py, reservations.py and redis_reservations.py all differed from the checkout. The backend script built APIs/workers but omitted simulator; Compose's per-service image persisted across force-recreate. Existing worker source gates omitted it too. The simulator image is an uncontrolled factor; the run is diagnostic and cannot certify a same-revision deployment, independently of its failed scheduling gates.
- **Decision:** Include simulator in the existing application build, recreate it with the existing baseline configuration during deployment and include it in active worker status/source verification before fixture dispatch. Preserve current simulator4 baseline, candidate8 override and rollback4, DB budget/topology and paid rate. Verify the existing workers/cache and repaired reservations/Redis intake modules like every other active worker. This extends the existing same-source deployment contract and supersedes its simulator omission in ADR0104; no accepted persistence/TTL/locking/messaging/scaling semantics change.
- **Alternatives:** Recreating only the container does not build its image. Inspecting only the command module misses imported business code. Promoting from the current mismatched run would certify uncontrolled source versions. Adding a second load automatically is outside this one-stage scope. Pinning every image to a registry digest remains broader future release work requiring its own decision.
- **Consequences:** Future deployments stop before load if any checked simulator module differs. An additional local image build/recreation adds setup work, not request latency. No performance improvement is claimed from this coverage repair.
- **Failure/recovery behavior:** Keep existing runner finally paths for fixture retirement, observer shutdown, original settings/budget restoration and private scratch cleanup. After this failed stage, repair and verify the baseline simulator separately, without new customer load or production topology promotion. Do not delete historical orders/tickets/outbox evidence or erase the failed scheduling/source verdict. A healthy process alone does not establish revision consistency.
