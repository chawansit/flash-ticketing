# 0115 - Persistent read-only Kafka observer for paid capacity tests

- **Status:** Accepted before implementation on 2026-10-03.
- **Context:** ADR0114 paid control saturated the four-core API host; Kafka CLI observations timed out eight times. A no-buyer idle/CLI/idle comparison measured Kafka container CPU0.299/0.864/0.167cores and hostCPU21.62/35.01/18.06percent, six CLI samples without errors. This is bounded mechanism evidence; broker background work and observer costs under paid load remain uncertain. Short SSH success/failure completion checks passed; the earlier480s transport timeout remains unexplained.
- **Decision:** Retain legacy CLI mode for existing callers; add a persistent Python mode and use it for the paid runner. Run within an existing API container using its already installed kafka-python library. One KafkaAdminClient describes group ownership and fetches committed offsets; a KafkaConsumer with group_id=None, auto commit disabled, no subscription/assignment/poll, auto topic creation disabled, and bounded request timeouts reads metadata/end offsets only. Reuse clients across samples. Compare group descriptions before/after observations, require stable unique ownership covering every configured topic partition and valid offsets. Negative/missing offsets, changing ownership, unknown topics or network errors produce failed samples, never fabricated zero lag. Preserve sample schema, ownership fingerprints and all strict startup/final Kafka gates. Duration remains bounded; close both clients on normal/error/signal exit. No customer retry or changes to booking/payment/TTL/delivery patterns. Replace only ADR0105/0114's paid Kafka observation mechanism; all acceptance gates remain in force.
- **Alternatives:** Increase CLI timeout, reduce sampling frequency, omit the Kafka gate, move Kafka immediately, or increase workers. These do not first remove the measured repeated JVM startup cost or confound the application comparison.
- **Consequences:** Two persistent read-only connections and small metadata/offset requests replace repeated JVM startup. Sequential group/offset views are not atomic; inconsistent views fail safely and invalidate the experiment. Sampled lag can miss brief peaks. Monitoring in an API container contributes to container CPU but not the API process counter. Legacy CLI callers are unchanged. No assumption that the capacity regression is entirely caused by monitoring.
- **Failure/recovery behavior:** Initialization/query failures are typed failed observations. Recreate failed clients for subsequent observations without hiding earlier errors. No subscribe, poll, commit, seek or group join calls. SIGTERM stops further samples and closes clients after bounded requests. Runner copies and cleans owned PID/log/trace/script files before baseline restoration. Every exact paid/unpaid postTTL, zero-double-booking, full-keyspace queue/Kafka/source/restoration/idle/private-cleanup gate remains required. Same8slots/60buyers per second/300seconds only; no90stage.
- **Validation evidence:** [Executed idle cost and SSH diagnostic](../capacity/flash-sale-opening/kafka-observer-cost-2026-10-03.json). Parser/ownership/error/cleanup/no-group regression tests, live CLI equivalence/cost comparison and same-load requalification pending. A failed load remains failed even if all backend tickets recover.
