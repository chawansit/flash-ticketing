# 0098 - Index unfinished payment deliveries

- **Status:** Accepted for a controlled candidate on 2026-10-03; no capacity promotion before measured gates pass.
- **Context:** The ADR0097 cache control failed at 45 offered paid journeys/s. Retained durable timestamps show payment-due to callback p95 of 15.82 s and callback to ticket p95 of 11.35 s, whereas callback-to-paid-event p95 is 36.18 ms and paid-event publication p95 is 120.86 ms. A bounded read-only plan found that an idle simulator claim scans all 63,832 payment attempts, removing every completed row; the table has only primary/unique order indexes. The unlocked equivalent touched 1,097 cached blocks and took 7.834 ms. This idle sample establishes unnecessary historical scan work, not loaded-query cost or the sole cause of either backlog.
- **Decision:** Add a B-tree on payment_attempts(due_at) with the partial predicate deliveries < target_deliveries. Preserve the exact existing due-time, lease, SKIP LOCKED, callback and acknowledgement queries; do not change threads, API budgets, polling, retries or Kafka processing. Delivered status cannot define the index: a SUCCEEDED payment may still require intentionally duplicated callback deliveries. Keep active leases in the index; lease eligibility remains evaluated by the query. Use an ordinary additive migration for fresh/local databases and a bounded concurrent index build for the already populated cloud database. Verify the index is valid and has the expected relation/key/predicate before testing. Do not alter historical migration files.
- **Alternatives:** Status=PENDING index (incorrectly excludes remaining duplicate callbacks); larger simulator pools (increases DB and HTTP pressure); replacing clock_timestamp with transaction time (changes due/lease semantics); continuous worker replenishment (separate scheduling pattern requiring phase evidence); splitting fulfillment consumers or changing Kafka partitions (does not address this historical payment scan and changes ordering/topology).
- **Consequences:** Completed payment history should no longer dominate claim scans. Each unfinished attempt contributes one index entry, removed on final delivery acknowledgement; this adds bounded index/WAL maintenance and does not bound a genuine large unfinished backlog. A due_at range condition may remain a filter because clock_timestamp is volatile; the partial ordered index still excludes completed history. This physical access decision extends the current durable dispatch design without superseding delivery idempotency, lease recovery, seat authority, outbox or Kafka semantics. Read-only timestamp tooling emits aggregate database-clock proxies, never actor/order IDs; it does not replace correctness audits.
- **Failure/recovery behavior:** A concurrent build has a 60 s statement timeout and 1 s lock timeout. A failed/invalid or structurally unexpected pre-existing index blocks the experiment; do not overwrite it or silently repair unknown infrastructure. An invalid index newly created by this action may be removed explicitly after inspection. Original claim/lease recovery works without the index. Revert a verified owned candidate using DROP INDEX CONCURRENTLY if correctness fails. If correctness passes and the query plan improves but customer gates fail, retain the valid index as an explicitly recorded schema improvement, restore service budgets/cache0, and report that the original database baseline changed. Never relabel a failed customer stage as passed.
- **Validation evidence:** Before implementation, five read-only analyzer integration tests passed after correcting a test envelope; cohorts cover 2,507 baseline and 2,456 cache-run payments. Index validation is pending: verify remaining duplicate callbacks and leased-attempt exclusion/recovery, full appropriate local suite, cloud before/after idle plan, then the same 45/s60s cache-enabled profile. Compare only this index against the prior cache-enabled stage. Preserve no retries, exact accepted-payment/unique-ticket post-TTL audit, zero double booking, Kafka/queue drain and configuration rollback. Stop higher-rate progression on a failed gate. No worker scheduling or consumer topology change is included.


Local validation before cloud application: all 348 unit/integration tests passed in 60.75 s using isolated PostgreSQL17.6 and Redis7.4.5; containers removed. This includes existing leased-payment exclusion and recovery checks, actual success plus two duplicate callbacks producing one booking/callback row, partial-index plan eligibility, and online verifier refusal of a conflicting index definition. Lint passed. Cloud concurrent build, after-plan and matched load remain pending.


Executed cloud outcome (source 3ae6bf7): concurrent build passed validity, key and predicate checks. The same idle unlocked query changed from 7.834 ms/1,097 cached blocks to 0.026 ms/one block. The same 45/s, 60 s cache-enabled control passed all 2,700 buyers with zero drops, zero customer HTTP errors and zero caller retries. Hold-to-ticket p95 fell from 22.57 s to 10.42 s; durable payment-due to callback p95 fell from 15.82 s to 236 ms. Callback-to-ticket p95 remains 8.39 s and Kafka lag peaked at 887 before draining to zero. The exact fresh audit after all hold deadlines passed with 2,700 payments/bookings/tickets, zero duplicates and empty queues. Source coherence, readiness, service budgets and cache0 were restored; the valid index is retained and recorded as a schema change to baseline. No higher-rate test ran. All 348 local tests passed before application; a reporting-only UTC/deadline-fence extension subsequently passed five focused integration tests and lint. This short-control pass does not certify hourly capacity or all latency SLOs.
