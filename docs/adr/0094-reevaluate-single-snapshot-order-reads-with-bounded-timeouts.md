# 0094 - Re-evaluate single-snapshot order reads with bounded timeouts

- **Status:** Rejected for promotion; implementation reverted after the failed controlled stage.
- **Context:** After generator correction, 45/s stages expose actual DB-pool saturation. Slower polling alone fails with 873 pool-full rejections and mean connection occupancy 35.31 ms. Each order GET enters a write-oriented transaction helper with explicit BEGIN, three separate timeout statements, two SELECTs and commit. ADR 0089's earlier single-query candidate was rejected under a generator that dropped work; it cannot establish behavior with the corrected generator.
- **Decision:** Change only order-status reads to the existing connection lifecycle with one transaction setup round trip and one actor-scoped SELECT returning tickets as ordered JSON. The setup enforces READ ONLY and retains lock_timeout 75 ms, statement_timeout 1500 ms and idle-in-transaction timeout 3 s via one static multi-statement command. Preserve commit/rollback and pool return through the existing connection context. The order and ticket list share one SQL snapshot. Leave all booking/payment/fulfillment mutations on their current transactions. Begin with isolated PostgreSQL integration checks and a 10-journey cloud smoke, then the same 45/s, 1s-poll profile; stop escalation if it fails.
- **Alternatives:** More DB connections (deferred: changes capacity budgets); unlimited waiters/retries (rejected: masks overload); Redis order projection/push channel (deferred: requires event ordering, actor isolation, stale-read/recovery and cache reconciliation decisions); simply restore the old candidate with fewer timeouts (rejected: maintain the existing timeout bounds).
- **Consequences:** Fewer statements/round trips may reduce connection occupancy; JSON aggregation adds database work. Ticket IDs become JSON strings at the adapter boundary; API output remains equivalent. Read-only setup limits accidental writes. Commit timing through the connection context is included in connection occupancy but is not the write-transaction commit histogram. No reduction or throughput improvement is claimed before measurement. This reopens ADR 0089 as a new controlled candidate; its historical rejection remains valid, and accepted locking/payment/outbox decisions are not superseded.
- **Failure/recovery behavior:** Missing/non-owned order returns the same ORDER_NOT_FOUND. SQL timeout/errors roll back via the connection context and release/reset the pooled connection. Empty ticket lists remain arrays; ordering remains by seat ID. Require authorization isolation, pending/paid/fulfilled response shape and timeout cleanup checks. On a failed real gate, preserve exact paid-ticket audit/queue drain and revert the candidate before any higher rate. Local integration containers must be isolated from existing applications and cloud datastores.
- **Validation evidence:** [Failed 1s-poll control](../capacity/flash-sale-opening/real-paid-slower-poll-control-2026-10-03.json) motivates the candidate. Executed: 91 selected unit/integration tests passed against isolated PostgreSQL 17.6 and Redis 7.4.5. A subsequent full-unit plus lock-timeout recovery run had 217 passes and one scheduler-sensitive mixed-load failure (one Windows scheduling drop at 51.7 ms); all four tests in that file passed on targeted rerun. Lock-timeout recovery passed, followed by successful reads/writes; changed-file lint passed. The two dedicated local test containers were removed. Cloud smoke passed:10/10 unique paid tickets, correctness/queue audit and rollback passed. Pool-full rejections fell873->72,mean connection occupancy35.31->28.00ms and successful acquisition50.25->16.23ms; this does not establish valid capacity. Post-TTL:2305 accepted payments/unique tickets,4 unpaid expired,zero duplicates,empty queues; Kafka lag drained to0 and configuration rollback passed. Candidate implementation reverted as required; authorization/timeout recovery integration checks are retained.
