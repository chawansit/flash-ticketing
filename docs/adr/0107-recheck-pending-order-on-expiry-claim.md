# 0107 - Recheck pending order state when claiming expiry

- **Status:** Accepted on 2026-10-03 before implementation; regression repair, locally verified before any cloud deployment.
- **Context:** The first full suite for ADR 0106 returned 373 passed / 1 failed in 78.63 s: two concurrent expiry batches counted four claims for three orders. Discovery changes do not execute this PostgreSQL path. A deterministic real PostgreSQL regression pauses an expiry SELECT after its READ COMMITTED snapshot is taken and before order locks, lets another worker expire all three orders, then resumes. The old query returns three already-expired orders (1 failed in 0.72 s). It filters only the unlocked joined hold's snapshot status. Rechecking the locked order version does not invalidate that stale hold predicate, so SKIP LOCKED alone is insufficient after a competing commit.
- **Decision:** Add o.status='PENDING' to the existing due-active-hold query, so the eligibility predicate includes the authoritative row being locked. Preserve FOR UPDATE OF o SKIP LOCKED, batch bounds, order-before-hold-before-seat locking, one transaction per batch and ownership checks. This supersedes ADR 0057's hold-only eligibility predicate; its batching, worker topology and transaction boundary remain accepted. No additional lock, isolation-level change, schema/index, TTL, payment or messaging pattern is introduced.
- **Alternatives:** Locking both joined rows broadens the lock set and needs separate deadlock/order analysis. Serializing all workers removes concurrency. Raising isolation or retrying batches adds unrelated transaction semantics. Ignoring the failed count leaves duplicate expiry outbox effects possible. An extra per-order query adds round trips when the existing locked-row predicate suffices.
- **Consequences:** An expiry worker cannot claim an order which another worker has already transitioned away from PENDING, including a completed payment. The active hold/deadline predicates still prevent early expiry; the existing ownership guards protect a reclaimed seat. No higher throughput is claimed without measurement.
- **Failure/recovery behavior:** A worker crash still rolls back the entire batch; SKIP LOCKED still avoids currently locked orders. Previously expired orders are excluded when the row is rechecked after a competing commit, preventing duplicate expiry counts and SeatsChanged events from this race. Existing replay/idempotency and payment locks remain required. No automatic historical outbox deletion or cloud data mutation.
- **Validation evidence:** The pre-fix deterministic snapshot/commit interleaving failed (raw ignored tmp/expiry-stale-reproduction.txt). The test requires the stale worker to claim zero orders and exactly three expiry events after the other worker commits. Full suite, discovery regressions, existing concurrent expiry/payment/reclaimed-seat/rollback tests and lint must be recorded after execution. The first suite failure remains recorded; no cloud load has run during these repairs.


Executed validation: the deterministic snapshot/competing-commit regression now passes: the first worker expires three orders, the stale worker claims zero, all seats are released and exactly three expiry outbox events are added. Existing concurrent expiry, payment, reclaimed-seat and rollback cases passed in the final full unit/integration run: 376 passed in 66.84 s, two existing dependency deprecation warnings. Changed-file Ruff, Python compilation and git diff --check passed. No cloud deployment, historical mutation or additional load stage was executed.
