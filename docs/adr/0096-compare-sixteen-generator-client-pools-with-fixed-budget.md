# 0096 - Compare sixteen generator client pools with a fixed total budget

- **Status:** Accepted for an isolated candidate experiment; no production application change or higher-load authorization.
- **Context:** ADR0095's clean 60/s diagnostic with eight pools per shard passed every journey, but each child used about0.92-0.93process CPU seconds per elapsed second, loop-lag p9535-39ms and hold pre-send p95755ms. Body-read p95 was below0.25ms; stream close including pool release was18-20ms. Prior profiling attributes significant costs to HTTPcore connection assignment/state scans. Instrumented and prior uninstrumented control completion timings were similar, but instrumentation overhead remains a limitation.
- **Decision:** Use the existing client-count option to compare sixteen pools per child against eight, preserving two processes, total500connections/active journeys,60/s for60s,0.2s polls,30ms responder delay,0.5s durability,5s fulfillment,diagnostics enabled and no retries. Split each child's250connections as ten16-connection pools and six15-connection pools. Do not change default client count, implementation or workload. Interpret only a valid responder and complete accounting pass; do not claim backend throughput from it. Retain the 20s fulfillment saturation result as evidence about cap pressure, not a candidate gate to relax.
- **Alternatives:** More total connections/processes (changes resources); patch HTTPcore scans (maintenance risk); abandon HTTPX (larger behavioral change); larger body buffers (not supported by measured tiny body cost).
- **Consequences:** More, smaller pools may reduce synchronous scans but add client/pool objects and idle connections within the same connection ceiling. Journey routing remains deterministic for its lifetime; no balancing between pools. CPUs and process counts stay fixed. Report exact configuration and compare all phases,CPU,loop lag and peak active journeys rather than one latency statistic.
- **Failure/recovery behavior:** Existing count/budget validation and AsyncExitStack cleanup apply. Preserve every drop/error and strict gate; close all synthetic connections and temporary manifests. A failure ends this candidate; do not change caps or retry to make it pass. Live API state remains unchanged.
- **Validation evidence:** Existing partition/cleanup and lifecycle tests passed; the full220-test suite passed on diagnostic revisione1f7828. Planned: clean-revision sixteen-pool control with the same diagnostics as the eight-pool baseline. Append executed evidence before selecting a future real-control configuration. Extends ADR0092's experimental parameter; no accepted production pattern is superseded.
