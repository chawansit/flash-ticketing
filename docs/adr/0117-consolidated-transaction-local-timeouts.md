# 0117 - Consolidate transaction-local timeout setup

- **Status:** Accepted for implementation and controlled evaluation on 2026-10-03; capacity qualification failed in the same-load control; retained only on the experimental branch.
- **Context:** The persistent-monitor paid control dispatched10485/18000 journeys, confirmed9764 to customers and returned721 customer503s. API aggregateCPU1.9524cores was the largest role on a96.61percent busy four-core host. MeanAPIconnection occupancy52.73ms and pool acquisition31.68ms; individual SET requests averaged4.55ms. Each common transaction currently executes explicitBEGIN and three separate SET LOCAL requests. This identifies avoidable setup round trips, not a proven attribution of all CPU or callback delay.
- **Decision:** Keep explicit BEGIN, then execute one static SELECT calling set_config for lock_timeout75ms, statement_timeout1500ms and idle_in_transaction_session_timeout3s, each with is_local=true. Yield only after all settings succeed; mark the transaction started immediately after BEGIN so setup errors receive explicit rollback. Keep commit, pool lifecycle, booking constraints, row-lock ordering, Redis atomicity, TTL, outbox, payment idempotency and budgets unchanged. This supersedes only the three-request setup mechanism in the common Postgres.transaction helper; no accepted ownership/durability decision is superseded. ADR0094's rejected order-read aggregation remains rejected; this change does not alter domain SELECTs or response shapes.
- **Alternatives:** Persistent session defaults risk leaking through transaction pooling. Removing safety timeouts weakens bounds. Psycopg pipeline or a multi-statement SET request introduces different protocol handling; one static SELECT provides one server statement and no configurable SQL interpolation. More connections, workers or retries confound this comparison.
- **Consequences:** Timeout setup goes from three requests to one, retaining the BEGIN request. The query histogram categorizes this request as SELECT rather than three SET samples: compare total statements/occupancy and operation timings, not category means alone. Pool errors and CPU may still be limited elsewhere; no throughput improvement is claimed before testing. The idle/statement safety deadlines begin within this setup request, as with the previous setup; transaction-local settings end on commit/rollback. No change to connection budgets or customer retry.
- **Failure/recovery behavior:** A setup error never yields the connection and explicitly rolls back. A body error/cancellation rolls back; no uncommitted booking/payment/outbox write is acknowledged. Broken idle-timeout connections are discarded/replaced by the pool. Local settings must not leak on successful or failed reuse. Source identity must include postgres.py in every running API/worker before dispatch and after configuration restoration. A failed paid gate remains failed; retire fixtures, finish exact paid/unpaid postTTL audit, full-keyspace queue/Kafka drain, readiness/source/idle/private cleanup, restore recorded service budgets and do not increase load. Implementation may remain on the experimental branch with explicit failed/unqualified evidence; no merge or production promotion is authorized by a failed load.
