# 0100 - Bounded paid-rate validation after lookup indexes

- **Status:** Accepted on 2026-10-03 before execution. User Continue authorizes the next proposed 60 buyers/s control only.
- **Context:** ADR 0099 completed 2,700 unique paid tickets at 45 buyers/s for 60 seconds, with zero customer errors/drops, successful post-TTL audits and drained queues. Hold-to-ticket p95 was 4.197 seconds and backend callback-to-ticket p95 698 ms. This does not validate the 300,000 tickets/hour target (83.33 successfully issued tickets/s sustained).
- **Decision:** Reuse the existing bounded cloud paid-stage runner and generator controls; do not extend orchestration or alter production patterns. Run one 60 buyers/s, 60-second control: 3,600 distinct one-ticket buyers, 12 isolated shows of 300 seats, 500 active-journey/HTTP connection budget, one generator process with 16 clients, one-second polling, no caller retries, one callback delivery/payment. Keep four APIs, pool 3/API, admission 4/API, waiters 12/API, three reservation writers with batches of four and 60-second maximum command age, eight simulator threads, four consumers, three-second advisory order cache, both validated indexes. Exact previous profile is in the ADR 0099 report. Twelve shows rather than nine are needed for 3,600 distinct seats: this also changes show distribution, so this is a staged-load comparison, not perfectly isolated rate-only causal proof. New fixtures must remain isolated and open throughout the deadline.
- **Alternatives:** Jumping to 83.33 or 100 buyers/s risks confounding overload without an intermediate baseline. A 45-second run at 60/s preserves the original ticket count but changes offered duration. Repeating 45/s with twelve shows would improve experimental isolation at additional cost; reserve that for ambiguous results.
- **Consequences:** More offered paid journeys may increase polling, callback and Kafka backlog. HTTP request rate is measured separately from successful issued tickets/s. One-minute success is a short control, not maximum/hourly capacity. The existing short-control pass checks completion, dispatch and correctness, not every latency SLO. No architecture decision is superseded; this extends validation scope beyond ADR 0099's 45/s candidate.
- **Failure/recovery behavior:** Stop at this stage on any failed customer/generator/preflight gate; do not increase rate or hide failures with retries. Use the existing runner's bounded completion and queue waits, fixture retirement, private-manifest cleanup and service rollback. Collect failure evidence without treating rejected/ambiguous requests as unpaid. Independently audit exact durable issued tickets and zero double booking after all original hold deadlines, plus empty reservation/outbox/dead-letter queues and final Kafka lag zero. Verify healthy baseline/source coherence after rollback; retain validated indexes separately from restored service configuration. Preserve evidence and investigate only the failed phase. A failure does not authorize speculative production changes.
- **Validation evidence:** Baseline: [ADR 0099 paid control](../capacity/flash-sale-opening/real-paid-booking-index-control-2026-10-03.json), tested source 53429c5. All 350 local tests were executed for that implementation; no new code changes are required for this stage. Planned: record source/configuration, offered and completed journeys, HTTP attempts, drops/errors/retries, client and durable phase p95, post-TTL audit, queue/Kafka drain and baseline restoration. No 60/s result is claimed before execution. Existing tooling decisions in ADR 0040 and ADR 0090 remain in effect.

Executed control at source `d78216a`: strict customer gate failed. Of 3,600 scheduled buyers, 3,576 dispatched (24 active-cap drops), 3,575 observed tickets and one order GET503; no caller retries. The durable backend issued all 3,576 accepted payments. Hold-to-ticket p95 was 14.044 seconds; callback-to-ticket p95 9.734 seconds; dispatch lag p95 4.710 seconds; Kafka peak lag 1,258, final zero. Fresh audits after all original hold deadlines confirmed 3,576 unique paid tickets, zero double booking/dead letters and empty queues. Baseline settings/cache0/readiness/source hashes verified after rollback; both validated indexes retained. No higher stage ran. No code changes or new local test run were needed. See [60 buyers/s control](../capacity/flash-sale-opening/real-paid-60-buyer-control-2026-10-03.json). Diagnose both backend fulfillment backlog and generator delay before increasing load; this failure is not proof of a unique root cause or an absolute backend ceiling.
