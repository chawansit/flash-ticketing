# 0089 — Use a bounded single-statement PostgreSQL order-status read

- **Status:** Rejected as a standalone capacity fix after a failed same-profile cloud stage; read path reverted on the branch.
- **Context:** The 60 paid-journeys/s, two-generator, 0.2-second polling stage issued 10,872 order GETs for 2,709 dispatched journeys. Fifty-three API pool acquisitions failed, with 43 order GET and eight payment POST 503s. A one-second polling candidate worsened DB-pool errors to 135, so cadence alone is not the remedy. The current `get_order` uses a write-oriented transaction helper (explicit BEGIN, three SET LOCAL statements, COMMIT) and then makes separate order and ticket SELECTs. That occupies a scarce three-connection API pool for extra network round trips. Mean connection hold across all API operations was about 29-30 ms, while a SELECT and COMMIT averaged about 3 ms each; route-specific savings are not yet measured.
- **Decision:** For `GET /v1/orders/{order_id}` only, acquire one pooled PostgreSQL connection, run a bounded read-only statement that selects the actor-owned order and aggregates its tickets from one statement snapshot, then return the connection through the existing context manager. Set a local statement timeout before the read to preserve a 1,500-ms database execution bound. Keep authorization in the SQL predicate, response shape and PostgreSQL as the source of truth. No Redis order projection or status cache is introduced. Preserve the existing write transaction helper for holds, payments and fulfillment. Compare identical 0.2-second polling profiles at the same offered rate and topology; report physical GETs, DB-pool errors, 503s, latency, completed tickets and post-TTL integrity.
- **Alternatives:** Adding DB connections could increase RDS contention and does not remove unnecessary round trips. Caching pending status in Redis requires invalidation, actor isolation, bounded staleness and a separate recovery design. A one-second client poll was tested and failed. Joining tickets in a second SELECT preserves the current two-round-trip read. Returning a provisional cache-only paid state would risk claiming a ticket that is not durable.
- **Consequences:** A single query sees a consistent statement snapshot of order status and issued tickets. `FULFILLED` should imply its ticket rows are visible because issuance and order transition occur in one PostgreSQL transaction. JSON aggregation changes the internal Python ticket-ID representation to text, but the HTTP JSON representation remains a string UUID. A read still uses PostgreSQL and the API pool; this is an optimization, not a capacity guarantee. The connection context commits/rolls back the read-only transaction and returns it to the pool. The read no longer inherits the write path's lock and idle-transaction limits; a statement timeout bounds the only read query.
- **Failure/recovery behavior:** If the query times out or the pool is full, preserve the existing non-success API behavior; do not return stale data or retry payment. A client repeats a safe order GET with its authorization token. If the optimized route fails a correctness or load gate, revert the branch change and restore the previous read path. Payment, booking and ticket uniqueness remain protected by their existing PostgreSQL constraints and idempotent callbacks.
- **Validation evidence:** The [0.2-second two-process control](../capacity/flash-sale-opening/paid-ticket-sharded-generator-2026-09-29.json) and [failed slower-polling candidate](../capacity/flash-sale-opening/paid-ticket-slower-polling-2026-09-29.json) motivate the experiment. Before promotion, execute unit/integration checks for actor isolation, pending/no-ticket and fulfilled/ticket response shape, then a same-profile 60/s cloud stage with exact post-TTL audit, queue drain and rollback. No measured improvement exists at decision time.

The candidate passed 208 unit tests and a 10-journey real-PostgreSQL
smoke. Its same-profile 60/s cloud stage then failed: 886 generator
drops, 57 DB-pool acquisition errors and 49 buyer-visible 503s. Mean
connection hold fell from 29.46 to 24.33 ms across separate runs, but
end-to-end throughput did not pass. The exact post-TTL audit found
2,700 paid orders with 2,700 unique tickets, 14 expired unpaid orders,
no duplicates and empty queues. [Redacted evidence](../capacity/flash-sale-opening/paid-ticket-single-query-order-read-2026-09-29.json).
Per the failure/recovery rule, this candidate is rejected as a capacity
fix and the read path will be reverted.

The branch source was restored to the two-query order read and the candidate-only unit test removed after the failed stage. The candidate remains documented for future comparison.
