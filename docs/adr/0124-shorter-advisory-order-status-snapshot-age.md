# 0124 - Shorter advisory order-status snapshot age

- **Status:** Accepted for an opt-in bounded configuration trial on 2026-10-04 under the user's overnight authorization ending 08:00 Asia/Bangkok. Not a production default or promotion.
- **Context:** ADR0122/0123's passing writer controls confirm all 18,000 purchases at 60 buyers/s for 300 s. The uninstrumented 3,000 ms cache control makes about four order GETs per purchase, with about two cache hits and two misses. Postpayment observation wait p95 is 3.159 s, while backend payment-due-to-ticket statement timing p95 is 448 ms. ADR0118's requalified profile reproduces the polls and shows distributed Python request/storage work; 70.81% of stacks lack endpoint identity. Unpaired timings and aggregate counts support a stale-snapshot hypothesis, not per-order proof.
- **Decision:** Compare existing ORDER_STATUS_CACHE_MS=1000 with the identified passing 3000 ms baseline, changing only maximum advisory snapshot age. Use the existing runner option and existing cache implementation; no application code change. Preserve 60 buyers/s, 300 s, two shards, 500 journeys and eight HTTP clients per shard, 1 s client polling, callback duplication=1, 60 shows and 18,000 unique actors. Preserve API4/pool4/waiters12, consumer6/pool8, writer3/batch4, simulator8/refill and PgBouncer24/reserve0/client160. Reuse ADR0040/0090 orchestration and ADR0123's bounded CPU collector. Omit the external stack profiler from the comparison to match the uninstrumented baseline. At most one initial trial and one identical confirmation, conditional on every initial gate passing, in this overnight window.
- **Supersession:** Partially supersedes ADR0097's initial controlled 3-second candidate for this trial only. The accepted opt-in range 0..3000 ms, default disabled, authorization/freshness/fallback contract and production qualification limits remain in force.
- **Persistence/locking:** PostgreSQL remains authoritative for payment, seat ownership, bookings and ticket issuance. No transaction, locking, connection limit or schema change.
- **Messaging/idempotency:** Outbox publication, Kafka handling, callback/payment idempotency, writer replay and uniqueness constraints are unchanged. A cached status never authorizes a mutation.
- **TTL:** Only the advisory actor-scoped order-status freshness budget becomes 1000 ms. Redis server-time/deadline accounting, SET NX fill, non-refreshing hits, old-fill protection, ownership/schema validation and outage fallback remain unchanged. Hold, seat, command and payment TTLs are unchanged. Existing Redis clock/failover qualification limits still apply.
- **Scaling:** No additional instances, CPU, connections, load, show skew or production capacity claim. Reduced customer polling is a hypothesis; higher database miss pressure is possible.
- **Alternatives:** Cache disabled may increase database work substantially; 500 ms is a more aggressive expiry before enough issuance evidence; longer client polling changes customer behavior and can hide API demand; terminal-only caching or mutation invalidation introduces a new application/replay pattern; moving authentication/handlers changes a different CPU factor. Defer these to separate evidence and ADRs.
- **Consequences:** A shorter PENDING snapshot may expose issued tickets earlier and avoid repeated polls. If fulfillment exceeds the freshness budget, more database misses may increase contention. Interpret HTTP attempts separately from completed paid tickets/s, and bounded sampled host/API CPU separately from native/function attribution.
- **Failure/recovery behavior:** Keep explicit errors and drops; do not retry customer journeys or raise load to hide failures. Reject any financial, durability, zero-double-booking, post-TTL, full-keyspace queue, Kafka, observer, CPU, source/settings/readiness, restoration, generator-idle or private-cleanup gate failure. After a failed initial trial, stop further overnight cloud experiments and diagnose offline. Existing runner finally restores baseline API cache0/pool3/waiters3 and worker budgets; independently verify restoration and owned scratch cleanup. No new cloud run after07:30; at08:00 only necessary cleanup/restoration of existing work, then handoff and pause.
- **Validation evidence:** Before the configuration trial, execute existing focused cache authorization/freshness/old-fill/fallback tests with isolated local PostgreSQL/Redis integration, plus relevant runner/CPU checks. Planned unchanged-load comparison must dispatch and customer-confirm all18,000 unique tickets without drops/errors/retries and pass fresh exact financial/linkage/zero-double-booking/full-queue/Kafka audits. Compare customer confirmation wait, HTTP/order polls, cache misses, API CPU and database pressure against [passing 3-second baseline](../capacity/flash-sale-opening/paid-writer-fairness-repeat-2026-10-04.json). Do not subtract unpaired backend/client percentiles as an exact stale-cache delay. Executed results will be appended; none are claimed for this trial yet.
