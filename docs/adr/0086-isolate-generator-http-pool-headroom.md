# 0086 — Isolate synthetic generator HTTP connection-pool headroom

- **Status:** Accepted as a controlled diagnostic; no production ingress or business-path change.
- **Context:** At 60 scheduled paid journeys/s, the shared generator client allowed at most 500 in-flight journeys and exactly 500 HTTP connections. A failed stage dropped 770/3,600 scheduled journeys and returned six buyer-visible checkout 503s. HTTPX traces recorded p95 6.10 s before sending hold request headers and 6.75 s before payment request headers. Response-header waits were 42/91 ms, while FastAPI `Server-Timing` was 11.91/60.44 ms. New TCP connects were uncommon. The client-side pre-send interval includes shared HTTP connection-pool waiting and scheduling overhead; the trace does not by itself prove which internal step dominates. A single pooled client is a generator artifact: independent real buyers do not all share its one connection semaphore.
- **Decision:** Add an explicit bounded `--http-max-connections` to the development paid-journey generator, defaulting to the existing in-flight cap. In a same-profile 60/s diagnostic, raise only the HTTP connection limit from 500 to 1,000. Keep the 500 journey cap, request schedule, 20 idle keep-alive slots, four API replicas, four Kafka consumers, simulator settings, one callback per payment and zero retries fixed. Report transport pre-send, response-header wait, app time, generator drops, checkout 503s, post-TTL exact tickets and rollback. A pass requires all strict gates; improvement in client timing alone does not certify production capacity.
- **Alternatives:** Raise the journey in-flight cap first could hide the generator queue while increasing request pressure and making comparison unclear. Increase API workers or RDS capacity would not target the measured pre-send delay. Put a waiting room in front of the API would address burst admission, but the current experiment is measuring a synthetic client artifact rather than selecting that production pattern. Split poll and checkout clients or increase keep-alive slots remains a later controlled experiment if connection headroom alone is insufficient.
- **Consequences:** The generator may open up to 1,000 sockets, though at most 500 journeys are active and each issues one request at a time. The generator ECS has 8 vCPUs, 16 GiB RAM and a 65,535 file-descriptor limit; the stage still needs runtime resource observation. A higher client limit may expose a previously hidden API/DB bottleneck. It must not be interpreted as an application throughput optimization.
- **Failure/recovery behavior:** On any strict failure, stop escalation, audit accepted and ambiguous payments after TTL, restore the original one-consumer/three-waiter/four-simulator deployment and retire synthetic fixtures. The client limit is process-local and disappears when the generator exits. No reservation, payment idempotency, Kafka delivery or TTL semantics change.
- **Validation evidence:** The motivating [redacted transport trace and corrected audit](../capacity/flash-sale-opening/paid-ticket-client-pool-trace-2026-09-29.json) show pre-send p95 above six seconds while FastAPI time is below 61 ms. The existing HTTPX trace hook was verified against a local HTTP server. The 1,000-connection comparison has not yet run at decision time.
