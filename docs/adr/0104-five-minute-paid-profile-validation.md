# 0104 - Five-minute validation of the paid profile

- **Status:** Accepted on 2026-10-03 before execution. User Continue authorizes one bounded five-minute stage at the same 60 buyers/s.
- **Context:** ADR 0103 passed 3,600 paid journeys during a one-minute offered window, with exact post-TTL tickets and restored settings. One minute is insufficient evidence of sustained stability. Its 12 shows provide only 3,600 unique seats; five minutes require 18,000 unique seats.
- **Decision:** Reuse the existing bounded paid-stage runner without changing application or orchestration patterns. Offer 60 buyers/s for 300 seconds, with 60 isolated shows of 300 seats and 18,000 actors. Keep the tested profile: four APIs/pool4/admission4/waiters12, six consumers/pool8 and one existing partition each, PgBouncer application pool24/reserve0/client160, three reservation writers/batch4/maximum command age60s, simulator concurrency8, cache3s, one generator process/500 active journeys and HTTP connections/16 HTTP clients/one-second polling, one callback delivery and zero caller retries. Existing completion deadline is420s and queue-drain budget120s. The runner already supports these limits; no code change is selected.
- **Alternatives:** Increasing rate now confounds duration with load and skips the stability check. A five-minute run on the old inventory would test sold-out/conflict behavior instead of distinct successful purchases. Increasing seats per show above300 changes the cinema model. Keeping only12 hot shows active via rolling inventory would require a separate generator design.
- **Consequences:** Show count and offered duration increase together to retain realistic300-seat shows and enough unique inventory. Concurrent per-show traffic is spread more widely; therefore this is not a clean duration-only latency experiment or proof for a single hot concert show. Compare completion, errors, generator scheduling, backlog/drain and sampled resource waits with the one-minute baseline, while explicitly recording distribution changes. A passed five-minute stage still does not establish hourly or maximum production capacity or every latency SLO.
- **Failure/recovery behavior:** Abort on preflight, readiness, budget or inventory mismatch; do not raise the rate or add caller retries. Use existing bounded execution/deadlines and stop after this one authorized stage on a failed gate. Preserve backend-proven payment counts; distinguish failed reads from lost payment. Audit every original hold deadline, exact paid tickets/expired unpaid orders, zero duplicates/extra paid events and all queues/Kafka drained. Retire the fixture and restore original API pools3/waiters3/cache0, one consumer/pool12, simulator4 and other original service settings, with source/budget/readiness verification. No permanent topology promotion.
- **Validation evidence:** Pending this stage. Application source is unchanged; previously executed 24 orchestration checks and earlier362-test application suite are historical evidence, not rerun here. Baseline: [ADR0103 short control](../capacity/flash-sale-opening/paid-api-pool-four-control-2026-10-03.json). Record the stage revision, compact results, exact post-TTL audit and restoration after execution. This records experimental scope and extends validation; no accepted persistence, locking, messaging, idempotency, TTL or scaling decision is superseded.
